# Architecture

How `runner-microvm` is put together: its processes, what flows between them, where code goes and which imports are forbidden, what it leaves on disk, how it fails and how each part is tested. Each decision carries its reason. The terms are the glossary's (`GLOSSARY.md`). The decisions that are hardest to reverse also have an ADR:

- [ADR 0002](adr/0002-job-process-with-vm-child.md): a job process per job, with libkrun in a VM child.
- [ADR 0003](adr/0003-plugin-talks-to-agent-directly.md): the plugin talks to the agent directly.
- [ADR 0004](adr/0004-libkrun-via-purego.md): libkrun is bound with purego.
- [ADR 0005](adr/0005-image-layers-are-erofs-files-on-one-virtiofs-share.md): image layers are EROFS files shared over one virtiofs share.

When the code and this document disagree, the same PR fixes one or the other.

## Today's limits are the plugin protocol's

forgejo-runner's plugin protocol passes the plugin a job's image, `cap_add` and `cap_drop`, its services (name, image, env, ports), the runner's per-label `backend_options`, the label argument and a timeout, and nothing else of the workflow's `container` and `services` spec. Whatever the plugin can't do today for that reason is a limit of the protocol, not a rule of this architecture: this document says so as "today, because the plugin protocol …", and shapes formats and seams so that lifting the limit adds entries or fields, not a redesign. As the protocol passes more, the plugin takes up whatever makes users' lives easier; what that looks like is decided then, not here.

## Programs

The repo builds three programs, each from a thin `main` under `cmd/`:

| Program | Runs on | What it is |
|---|---|---|
| `runner-microvm` | the host | the plugin: serves the runner, owns what jobs share (image cache, queue, memory budget) |
| `runner-microvm-job` | the host | the job binary: the job process, with `vm` a VM child, and with `libs` the startup check of libkrun and libkrunfw |
| `runner-microvm-agent` | inside the VM | the agent: boot mounts, Exec, CopyIn, CopyOut |

The job binary and the agent are embedded in `runner-microvm`, so there is one file to ship and the three can't drift apart in version.

## Process model

```
             runner (forgejo-runner)
                │  BackendPlugin gRPC, unix socket
                ▼
 ┌─────────────────────────── plugin ───────────────────────────┐
 │ gRPC server · job table · image cache · queue · memory budget │
 └──┬───────────────────────────────────────────────────┬───────┘
    │ control channel                                   │ agent protocol (gRPC)
    │  stdin:  job spec (protodelim)                    │  over <runtime>/<id>/<n>/ agent socket,
    │  stdout: status events (protodelim)               │  which libkrun maps to the guest's
    │  stderr: job process log file                     │  vsock port
    │  fd 3:   liveness pipe                            │
    ▼                                                   │
 ┌──────────── job process (one per job) ────────────┐  │
 │ job network (gvisor-tap-vsock) · disk locks       │  │
 └──┬────────────────────────────────────────────────┘  │
    │  stdin:  VM child spec (protodelim)               │
    │  fd 3:   liveness pipe                            │
    │  fd 4:   its VM's end of the job network socket   │
    │  fd 5+:  each disk's file, in the spec's order    │
    │  stdout, stderr: its VM's log file                │
    ▼                                                   │
 ┌───── VM child (job binary `vm`), one per VM ──────┐  │
 │ libkrun (purego) → VM; console → console file     │  │
 │   ┌──────────────── VM ─────────────────────┐     │  │
 │   │ agent ◄─────────────────────────────────┼─────┼──┘
 │   │  └─ steps, in the job's container       │     │
 │   └─────────────────────────────────────────┘     │
 └───────────────────────────────────────────────────┘
```

### One job process per job, with libkrun in a VM child

- **Each job has one job process, which owns everything belonging to it:** its job network, its VM children, its disk locks and its files. Ending the job process ends the job. The plugin keeps only what jobs share.
- **libkrun runs in a VM child the job process starts, one for each VM, not in the job process itself.** `krun_start_enter` never returns, and libkrun ends the whole process when the guest stops. In a child, libkrun's Rust threads never share an address space with the Go code that owns the job network and the disk locks. The job process also outlives its VMs, so it can report why each one stopped. See [ADR 0002](adr/0002-job-process-with-vm-child.md).
- **The VM child is the job binary run with a `vm` subcommand.** The plugin passes the job binary's own path in the job spec, so nothing ever execs `os.Executable()`, and a test binary can't recurse.
- **Each VM child's inputs:**
  - stdin: its VM child spec, one length-delimited protobuf message, in a memory file (`memfd`), not a pipe, so no goroutine of the job process copies it in and a VM child that never reads it, or a process it left holding stdin, can't keep the job process waiting;
  - fd 3: the liveness pipe;
  - fd 4: its VM's end of the job network's frame socket (Job network, The VM's link, below);
  - fd 5 and up: each of its VM's disks' file, in the order of the VM's disks, which the job process opens before it starts the VM child, read-only for a read-only disk, and takes its disk lock on. A `flock` belongs to the open file, which the VM child inherits, so the lock lasts as long as any process that can use the disk. libkrun attaches each by its descriptor's path (The boot root and the guest's root, below);
  - stdout and stderr: its VM's log file. libkrun's console goes to its VM's console file.

### One job process runs all of a job's VMs

- **One job process runs every VM of its job, each in its own VM child, all on the one job network:** the job's container, and each of its services once forgejo-runner's plugin protocol can pass options to configure them. The job spec holds what is job-wide (the job, the job binary, the library directory and the job network) and a list of VMs, each with its own shape, scratch disk, log and console files, agent socket, root and layer link directory, mounts and disks, address and MAC on the job network, and boot config. A service brings its own image and options, so none of these can be job-wide.
- **The first VM in the job spec is always the job's container.** The plugin's Exec and Copy go to its agent, because the plugin protocol's Exec and Copy name only the job, not a VM. A VM is ready when its agent answers Ping; today the job's container is the only VM, because the plugin protocol passes no VM options for services, so its agent is the only one the plugin dials.
- **A VM is identified by its index in the job spec: 0 is always the job's container, and services follow, in order.** The index names the VM's directories (On-disk layout, below), its key in the image cache seam (`Acquire`), and the VM in status events. An index is chosen by the plugin, so a workflow can't make two VMs collide or make a path leave its directory.
- **Each VM also has a name, unique within the job: its hostname, its name in every VM's `/etc/hosts`, and its name in log lines and `Failed` reasons.** It is never a path component or a cache key, because a service's name would be its key in the workflow, which the workflow chooses and which may be `job` or `0`, made DNS-safe. The job's container's name is the job's name made DNS-safe (Job network, Hostname and name resolution, below).
- **The job's container exiting ends the job.** The job process then kills the other VM children, reports each one's `VMExited` once it is reaped, and exits. What a service VM exiting does to the job is decided with services.
- **A disk named twice in one job, where either is read-write, fails Create, with `disk <source> is attached more than once in job <id>: a disk attached twice must be read-only both times`.** One process can't hold an exclusive and a shared `flock` on one file through two opens (an exclusive lock blocks every other open's lock, even in the same process), nor two exclusive ones, so the job process couldn't lock it for both VM children; and two VMs writing one block device, or one reading it while another writes, corrupt it. A disk named twice read-only both times may be shared between a job's VMs, because two shared locks don't block each other, even in one process (STO-8).
- **Today the job spec always holds exactly one VM, the job's container,** because the plugin protocol passes a service only its name, image, env and ports, and no VM options: a job that declares services fails at Create (PROTO-6, a limit of today's plugin protocol), and the job process rejects a spec whose VM count isn't one. The shape is built for more: services become more VMs of the same job, each another entry in the job spec's VMs, on the same job network and in the same job process, and that shape needs no redesign. What a service needs beyond it is added fields and calls, for example its entrypoint and `cmd` at boot and the plugin dialling its agent. Where a service VM's shape and storage come from is decided when services are.

### Children die with their parent

- **Every child gets a liveness pipe and `Pdeathsig: SIGKILL`.** The pipe is the primary signal: its closing tells a job process or VM child that the plugin is gone. Pdeathsig is the backstop, because the kernel kills the child even when its Go code is stuck in libkrun.
- **Children are forked from a dedicated, locked OS thread.** Pdeathsig fires when the forking *thread* exits, not the process, so a goroutine that happened to fork on a short-lived thread would kill its child early. The thread is never the process's main thread, which the Go runtime parks rather than ends, so the thread's own exit, as its tests stop it, fires its children's Pdeathsig as the process's death does. The launcher's thread lives as long as the plugin: as `serve` returns, after every job has ended, or when startup fails after making the launcher, the plugin closes the launcher, which ends the thread and closes both ends of the liveness pipe. A job process forks its own children, each VM child and mkfs, the same way, from a thread of its own that lives until its run ends, by when every child has been waited for.
- **The plugin has one liveness pipe, made by the job launcher at startup. Every job process gets its read end as fd 3; only the plugin holds the write end, close-on-exec, and never writes to it.** So the pipe reads end of file once the plugin is gone, however it died, and no other child of the plugin can keep it open. One pipe, not one per job, because what it signals, the plugin's death, is the same for every job. (Flagged decision, #52: rejected one liveness pipe per job, which costs two fds and a close for every job to say the same thing.)
- **A job process makes fd 3 close-on-exec at once, and reads it until it ends; then it logs `the plugin is gone` and sends `SIGKILL` to its own process group,** which ends its VM children and a running mkfs with it. A job binary started without a pipe on fd 3 exits with an error rather than run a job nothing can end. Being open is not enough: when fd 3 is free at exec, Go's runtime keeps a file of its own there (its cgroup's CPU limit), so fd 3 must be a pipe. (Flagged decision, #52: rejected running without the watcher when fd 3 isn't a pipe, which would leave a job process, and its VMs, that outlive the plugin.)
- **A job process hands the liveness pipe on to each VM child as its fd 3. A VM child reads it from its start, before its spec, and when it ends sends itself `SIGKILL`,** whatever its libkrun threads are doing. A VM child whose job process was killed outright dies of Pdeathsig, since the job process's forking thread died with it.

### Running without privileges

- **VM processes run as the plugin's user, in no user namespace. The design needs read-write `/dev/kvm` and nothing more: no subordinate ids, setuid helpers, TAP devices, bridges, firewall tools, loop devices or host kernel EROFS support (VM-9, #11).** This is a requirement, not a prototype choice: the plugin makes no assumption about where it runs (a container, a privileged container, bare metal), and each of these is something a container or an unprivileged host may lack.
- **The `kvm` CI job runs as the ordinary runner user, and that is the proof the whole design needs nothing more.** One test also checks that the job process and each VM child of a started job run under the plugin's uid with an empty effective capability set (Tests, below), which catches a setuid helper or a file capability creeping in.

### Running as root

- **The plugin runs identically as root (VM-9), and its code never branches on its uid.** Root has every permission an ordinary user has, so a bug on a path the ordinary user takes shows up in the ordinary-user run.
- **The one path root takes otherwise is libkrun's virtiofs server, which as root switches to the guest's uid and gid for each request** (STO-3's "files get the guest's uid and gid"). It serves every VM's boot root and layer share, not only the profile's mounts, and the ordinary-user run never takes it.
- **So only the tests on that path also run with the plugin as root, beside their ordinary-user runs, not the whole KVM suite:** the protocol test's root case (the echo workflow, then the profile check and reload), the Start time test (#103, which adds it), and the read-write mount test's root case (#89). A second CI job rerunning every KVM test as root would mostly prove the same thing again, at twice the KVM CI time. Each starts `serve` under `sudo -n` through one helper, skips saying why without passwordless sudo, and fails instead with `CI` set; the `kvm` CI job has passwordless sudo, so CI always runs them (Tests, below).

### The control channel: plugin ↔ job process

- **The control channel carries only a spec in and status events out:**
  - stdin: the job spec;
  - stdout: status events: network up, then for each VM, VM started and VM exited (with its exit code and the last 4 KiB of its console and VM log, as valid UTF-8, which a proto string must be), each naming the VM by its index in the job spec; failed (with a reason, and whether only the plugin's bug can cause it);
  - both as length-delimited protobuf (`protodelim`);
  - stderr: the job process log file;
  - fd 3: the liveness pipe.
- **It is not gRPC,** because one message in and a handful out don't need a server.
- **No spec appears on a command line,** neither the job spec nor the VM child spec. A command line is visible to every user on the host, and the spec may carry values that must not leak (LOG-2).

### The plugin talks to the agent directly

- **The plugin dials the agent over the unix socket libkrun maps to the guest's vsock port,** in the VM's runtime directory, `<runtime>/<id>/<n>/`. Exec and Copy go to the job's container's agent, because the plugin protocol's Exec and Copy name only the job, not a VM. The job process relays no streams, so there is no streaming relay to write and maintain. See [ADR 0003](adr/0003-plugin-talks-to-agent-directly.md).
- **A VM is ready when its agent answers Ping,** which the plugin learns by dialling the agent, not from a job process event. Today the job's container is the only VM, because the plugin protocol passes no VM options for services, so its agent is the only one the plugin dials.
- **The agent protocol is gRPC.** Cancelling a stream cancels the agent's context, which kills the step's process group (GST-8) with no extra code, and gRPC is already a dependency through the runner's protocol.
- **Cancelling a step sends `SIGKILL` to its process group only, at once (GST-8).** There is no per-step cgroup, and a process that left the group lives until the VM is removed. The agent starts each command as the leader of a group of its own, and its Exec's context ending kills that group; the plugin's Exec cancels the agent's call when the runner cancels its own.
- **The agent listens on vsock port 1024, a value only the plugin sets.** The plugin puts it in the job spec, for libkrun's port mapping, and in the boot config, which the agent reads before it listens. One value in one place can't be two constants that disagree.
- **A VM is ready when its agent answers Ping, which it does only after its boot work is done:** it listens only once its root, mounts, directories, network and names are made, so every call finds the guest prepared.
- **The agent has 30 s to answer. The plugin redials every 10 ms at first, at most every 100 ms, each attempt bounded by 500 ms, and stops waiting at once if the VM exits.** Boot takes about 2 s; 30 s leaves room on a loaded host. Until the agent listens, libkrun accepts and drops each connection, hence the quick redials. Start then fails naming the VM and the timeout, with the console and VM log tails.

### Ending a job: the whole process group, reaped

- **Each job process leads its own process group, and its VM children stay in it.** Killing a job is one `SIGKILL` to that group.
- **The plugin is a child subreaper (`PR_SET_CHILD_SUBREAPER`, set once at startup).** A VM child is the job process's child, not the plugin's. Without the subreaper, a VM child whose job process is killed is reparented to init, nothing in the plugin can wait for it, and it still holds its disk `flock` (fd 5+) while the kernel frees its guest memory. As subreaper, the plugin inherits it and reaps it.
- **The job process holds each VM's disk locks until that VM's child has exited, and the VM child holds them too, by the files it inherits; if either dies first, the kernel releases its hold with its files (#3).** So a crash can't leave a disk locked: a disk is locked only as long as a process that can use it lives, and the subreaper and the group reaping below guarantee those all end with the job.
- **A job's disks are freed only once every process in its group has exited and been reaped.** When the job process exits, killed or on its own, the launcher sees it with `waitid(WNOWAIT)` without reaping it, so the group id can't be reused; then it sends `SIGKILL` to the group, reaps the group's processes (`wait4(-pgid)` until no child in the group is left), and only then closes `Exited`. `Kill` returns only after that. So Remove frees the job's disks in the queue (QUE-7) only when no process can still hold their locks, and the next job waiting on a disk (QUE-3) never fails Start with `in use`. The liveness pipe and Pdeathsig say when a VM child must die, not when it has, and a job process killed by `SIGKILL` can't wait for its own child, so neither gives this guarantee.

### The flush

A job with read-write storage that ends normally has its VM flushed before it is killed, so the next job on the same disk or directory sees its data (STO-9). A VM that is killed instead is never flushed: its last writes may be lost, and the next job on its disk still mounts it (STO-10).

- **The flush is the agent protocol's own `Flush` call, not a `sync` command run through Exec.** It is the agent's job, not a step's, and needs no argv, user or `PATH`.
- **The agent's `Flush` runs `sync()`, then `FIFREEZE` on each read-write disk's mount, and never thaws them.** `sync` writes the guest's dirty pages to virtio-blk and virtiofs, and libkrun answers the guest's flushes with `fsync` of the host's files. The freeze also commits ext4's journal and marks the filesystem clean (no `needs_recovery`), so the next mount needs no recovery, and a read-only disk refused for a dirty journal (The boot root and the guest's root, below) then only meets a real crash. The VM is killed right after, so nothing needs a thaw. Without the flush, the spike lost the guest's writes and the next VM saw an empty disk.
  - **The agent records each read-write disk at boot: its target, where the target landed, and its block device's number, read as it probes the superblock.** At `Flush` it opens the landing place in the job's root and freezes it only when the open directory's filesystem is that device's: a step may have unmounted the disk, which leaves it clean already, or mounted something else over it, which must not be frozen in its stead. Opening the place afresh, rather than holding a descriptor from boot, leaves a step free to unmount the disk. A filesystem an earlier `Flush` froze (`EBUSY`) is no error.
  - **A disk that can't be frozen fails `Flush` with `FailedPrecondition`, naming its target, after the others are frozen;** a read-write mount needs nothing beyond the `sync`.
- **Remove calls `Flush` on the job's container's agent before it kills the job process, only when the job's profile gives the VM a read-write mount or disk.** A VM without read-write storage has nothing to keep, so its Remove stays as fast as before. The environment timeout backstop removes through the same path, so it flushes too (PROTO-14), and so does Close, as the plugin stops.
- **The flush has 30 s. A flush that fails or times out is logged, naming the job and the error, and Remove carries on and succeeds.** The runner can do nothing with a failed Remove, and the job is ending either way; 30 s is ample for a sync and a freeze. The flush also ends at once when the VM dies meanwhile, so a hung guest costs one job at most 30 s of its Remove, and never the plugin: the agent's `sync` may stay blocked in the guest, which the kill then ends.
- **Once Remove has taken a job out of the table, its flush and kill are the server's, not the call's: they run to their end whatever becomes of the call, and Close waits for every such removal before it returns.** The plugin's stop cancels every call at once, and a Remove whose flush its cancellation cut short, then whose VM the liveness pipe's closing killed, would lose the last writes of a job that ended normally. The cancelled call itself returns `Canceled` at once, so no handler outlives its context; the runner can do nothing more with that Remove either way. The flush keeps its 30 s, so a stop still waits at most one flush timeout for a hung guest, whether Remove or Close began its removal.
- **The flush is skipped when the plugin already knows the VM has exited:** the job's container's VM exited event, or its job process failing or exiting (The plugin server's calls, below). Otherwise a call to a dead VM's agent fails at once, as its socket has no listener, so a VM that died a moment before still costs nothing.
- **A failed Start kills at once, with no flush** (A failed Start, below), and Remove after it flushes nothing: its VM is gone.
- **Close removes every job at once, each as Remove does, rather than one after another.** One VM whose flush hangs then costs the plugin's stop its own 30 s, not 30 s for every job before it. (Flagged decision, #92: rejected keeping Close's removals in turn, which makes a stop with several hung guests wait 30 s for each, and skipping the flush at Close, which loses the writes of every job still running when the plugin stops.)
- **After a kill, the next job on a read-write disk mounts it read-write and its mount replays the journal (STO-10).** A killed VM child, job process or plugin leaves no lock held (Ending a job, above), and the disk may need recovery, which a read-write mount does.

### Start's progress

- **Start writes progress lines as `StartOutput` data on stdout, each `[runner-microvm <seconds since Start>s] <text>`, with the seconds to two decimals (PROTO-9):**
  - `image <ref> ready (<digest>, <n> layers) in <t>`, timing the image cache's `Acquire`;
  - `VM <name> (<cpus> CPUs, <memory> MiB) ready in <t>`, timing the job process's launch to the agent's answer;
  - `started in <t>`, just before StartComplete.

  The runner writes them to the job's setup log, and the prefix tells them apart from the runner's own lines.
- **A failed send of a progress line doesn't fail Start: only StartComplete must arrive.** The failure is logged. A send still blocked when Start's context ends may still run, and a stream takes one send at a time, so Start then sends nothing more and fails with its context's code. A Start whose context ends once its VM is ready, while it sends `started in` or StartComplete, is a failed Start like any other (A failed Start, below): the runner never took the job as started.
- **Once StartComplete's send has returned without error, Start has succeeded, whatever its context does afterwards.** The runner cancels Start as soon as it reads StartComplete, so that cancel can arrive while the send returns, and a Start that then failed would kill a job the runner already took as started. When Start's context ends during the send and the runner has ended the stream, Start waits for the send's own result: gRPC ends a blocked send as soon as its stream ends, so the wait is short. When only Remove or the VM's death ended it, with the stream still open, the runner may never read again: a send that has already returned still wins, and one still blocked fails Start. A Start whose context ended before StartComplete was sent sends nothing more. Exec's and CopyIn's last messages need no such rule: a failure after them changes nothing the runner sees, while a failed Start tears its job down.

### A failed Start

- **Start's progress lines are decided in Start's progress, above:** `[runner-microvm <seconds>s] <text>` on stdout, because the runner shows stdout in the job's setup log and the prefix tells the plugin's lines from its own; a line that can't be sent doesn't fail Start, because only StartComplete must arrive; a Start cancelled while it sends the last line or StartComplete fails, and is cleaned up, like any cancelled Start, because the runner never took the job as started; and a Start whose StartComplete send returned without error has succeeded, even when it was cancelled meanwhile, because the runner took the job as started.
- **A Start that fails because of the image, the VM's boot, the agent not answering, the job network, a mount's source, the scratch disk or a disk fails with `FailedPrecondition` (PROTO-10).** The runner treats `Unavailable` as "the plugin is gone" and retryable, and these failures are the job's or the operator's, not the plugin's. So is a job process that can't be launched, or a boot root that can't be written: the host's to fix.
- **A job process's `Failed` event says whether only the plugin's bug can cause it (`bug`): a job spec it can't read, or that doesn't describe exactly one VM.** Start then fails with `Internal`, naming the reason as the job process gave it; every other `Failed` is `FailedPrecondition`. The job process is the only one that sees the spec fail, and only the plugin writes the spec. (Flagged decision, #54 review: rejected matching the reason's text in the plugin, which ties a status code to wording, and a distinct exit code, which the launcher doesn't report.)
- **A Start cancelled by the runner, or by Remove, fails with its context's code: `Canceled` or `DeadlineExceeded`.** That says what happened. A send that the stream's end cuts off can fail before Start's own context reports its end, as Go ends a context before the contexts derived from it, so Start also takes the code from its stream's context once that has ended.
- **`Internal` is only for the plugin's own bugs** (a VM address it can't compute, an agent client it can't make, a job spec the job process can't read or that doesn't describe a job). Everything else names a cause the job log's reader can act on. **`Unavailable` is used only once the plugin is shutting down:** a Create during a drain (Stopping: the drain, below).
- **The message names the cause first,** because the runner shows the status message in the job log:
  - `image <ref>: …`;
  - `job process: …`, when it can't be launched;
  - `network: …`, `mount <source>: …`, `scratch disk: <path>: …` and `disk <source>: …`, the job process's `Failed` reason as it gave it; the scratch disk's path names its VM's directory;
  - `VM <name> exited during boot (<code>)`;
  - `VM <name>: the agent did not answer within <timeout>`;
  - `VM <name>: its job process exited during boot`, when it exited with neither a VM exited event nor a reason.
- **For a VM that exited, never answered, or whose job process exited during boot, the message then carries the last 20 lines of the VM log and of the console, each from at most their last 4 KiB, with their newlines, on the lines after a `VM log:` and a `console:` heading.** An empty one, heading included, is left out. 300 bytes on one line, the prototype's rule, often cuts off a kernel panic; the job log shows several lines fine. The text loses its carriage returns and any invalid UTF-8, and the plugin cuts it to size whether the VM exited event's tails or the files themselves are its source: what the guest writes is not trusted to be short. The files are read for an agent that never answered or a job process that exited, which sent no tails. (Flagged decision, #54: the ticket names the output only for a VM that exited or never answered; a job process that exits saying nothing, killed or crashed, leaves the VM's own output as the only clue to why. Rejected the bare `its job process exited during boot`, which gives the reader nothing to act on.) A call on a job whose VM died after Start carries the same output (The plugin server's calls, below).
- **A failed Start kills the job process's group at once and waits until it is reaped.** That drops its VMs, job network and disk locks without waiting for the runner's Remove.
- **A job whose Start failed is never started again.** A second Start fails with `FailedPrecondition`, naming the first failure: the failed Start left the VM's files half made, and the runner removes such a job rather than starting it again.
- **Remove then only deletes files and frees queue places,** with no flush (The flush, above), and does nothing harmful when the job process is already gone. A job's disks are still freed exactly once (QUE-7), and only after its group is gone.

### The plugin server's calls

How the plugin answers the runner's calls under the runner's real calling patterns: a call cancelled and followed at once by Remove, a job the runner forgets, calls that wait silently, and many jobs at once.

- **A step's relative working directory is taken from the job's workspace, the Exec's `GITHUB_WORKSPACE`, when that is absolute; otherwise the plugin passes the working directory on unchanged, and the agent refuses a relative one (Exec, below).** The runner sends a step's relative `working-directory:` as written. Its own container backend takes it from the container's working directory, which is the same path it gives steps as `GITHUB_WORKSPACE`, and today, because the plugin protocol passes the plugin no working directory of the job's, the request's environment is the only place that base reaches the plugin. (Flagged decision, #55: rejected taking it from the image's `WORKDIR` or `/`, which puts a step's files outside its workspace, and refusing it, which fails every workflow that names one.)
- **Exec, CopyIn and CopyOut before Start completes fail with `FailedPrecondition` (PROTO-11).** The job exists but can't take the call yet; the runner reserves `NotFound` for an unknown id. A job whose Start failed is in the same state. A call made while Start is still in progress fails at once, without waiting for the job's lock: the job records that Start has booted its container outside the lock, and the call reads that first, so it never waits out a pull and a boot and then runs once they succeed.
- **A call waits for its job's lock only while its own context runs.** Start, Exec, CopyIn and CopyOut each hold the job's lock for their whole length, so a call can queue behind another on the same job; one cancelled while it waits returns its context's code at once.
- **Remove of an unknown id returns `NotFound` (PROTO-12).** The runner relies on it. Remove of a known job flushes its VM when it has read-write storage (The flush, above), ends its job process and deletes all of its host files: `<state>/jobs/<id>/`, `<runtime>/<id>/` and, through the image cache's `Release`, `<cache>/jobs/<id>/`. Freeing its queue places and disks is #10's.
- **Remove succeeds while a cancelled Start or Exec of the same job still unwinds (PROTO-13).** It takes the job out of the table, cancels every call on it, then waits for the job's lock, which the unwinding call releases once it has stopped what it began (a cancelled Start its job process, Ending a job, above), and only then tears the job down. Neither call reports an internal error: each returns its context's code. A cancelled Exec releases the lock as soon as its agent call is cancelled, so Remove returns while the agent still unwinds the command. A cancelled Start releases it only once the image cache's `Acquire` has returned, so Remove waits for that unwinding: `Release` must wait for the job's `Acquire` before it deletes the link directories (IMG-14), and Remove must end any job process the Start launched before it returns (PROTO-12). Remove arriving mid-unwind is held, not refused. (Flagged decision, #51 review: rejected handing the teardown to the unwinding call so Remove returns at once, which would let Remove succeed with the job process still running and its disks still locked, QUE-7.)
- **A job whose VM has died: every Exec, CopyIn or CopyOut in flight, and every later one, fails with `FailedPrecondition` `VM <name> exited (<code>)`, then the VM's last output as a failed Start's error carries it (A failed Start, above).** The plugin learns it from the job process's VM exited event, not from a broken agent connection, whose `Unavailable` the runner reads as "the plugin is gone" and may retry. The output is the VM exited event's tails, as a failed Start's is. Remove then works as usual.
  - Once Start succeeds, one goroutine per job reads the job process's events; Remove waits for it after the kill, once the job process's events have ended. At the job's container's VM exited, a `Failed` event (`VM <name>: its job process failed: <reason>`), or the job process exiting with neither said (`VM <name>: its job process exited`), it marks the job gone, cancelling every call in flight on it with that status as the cause, and logs it, unless Remove caused it.
  - A failing agent call is how a call first sees its VM die, moments before the job process has reaped the VM child and reports it, and the failure need not be a broken connection's `Unavailable`: a stream the dying VM resets fails with `Internal`. So a call whose agent fails, for any reason but the call's own end, waits up to 10 s for the VM exited event, and fails with its status. A failure other than `Unavailable` waits only if a Ping, which doesn't wait for the agent to be ready, shows the agent gone; an agent that answers is alive, and the call fails at once with the agent's own error, so an agent's ordinary error (a bad tar) costs no grace. An agent that ends an Exec without an exit code fails it with `Internal` `VM <name>: its agent ended Exec without an exit code`, through the same path: the agent ships in the plugin, so its bug is the plugin's own. **The agent is libkrun's workload, so a VM whose agent is gone exits; if no exit is reported within the 10 s, the call fails with `FailedPrecondition` `VM <name>: the connection to its agent broke, and the VM has not exited: <err>`.** (Flagged decision, #51: rejected passing the agent's `Unavailable` on, which the runner reads as the plugin being gone, and `Internal`, which is for the plugin's own bugs. Flagged decision, #51 review: rejected waiting the grace on every agent failure, which costs 10 s on each of the agent's ordinary errors, and waiting only on `Unavailable`, which hands the runner a reset stream's raw `Internal` instead of the VM's exit.)
  - A call that Remove ends returns `Canceled`, whether or not its VM died meanwhile: Remove kills the VM itself.
- **The environment timeout backstop removes the job at the runner's `environment_timeout` plus 30 s, if the runner hasn't (PROTO-14).** 30 s leaves the runner its own Remove first. A missing or zero timeout sets no backstop; one too large to add 30 s to waits as long as a timer can (about 292 years), rather than overflowing to a negative wait that fires at once. The backstop does exactly what Remove does and logs that it fired; Remove stops its timer; a Remove after the backstop gets `NotFound`, as for any unknown id.
  - The timer starts at Create, which is when the runner sends the timeout, and its job enters the table with it. When it fires, it removes the job only if the job is still in the table, so it never races Remove or Close for one; Close waits for a backstop removal already under way.
- **Keepalive: the server accepts client pings every 5 s or slower, also with no call in flight, and sends no keepalive pings of its own (PROTO-15).** The runner pings every 30 s; grpc-go's default policy (5 minutes) answers that with GOAWAY `too_many_pings`, which cuts off a silent call. Its own pings would be a second liveness check the runner already makes, so its keepalive time is the longest duration, which never passes.
- **The plugin accepts messages up to 32 MiB.** That's the runner client's own limit, so nothing the runner may send is refused.
- **The agent keeps gRPC's 4 MiB message limit, and the plugin re-chunks copies to 256 KiB toward it.** CopyIn splits each of the runner's chunks into messages of at most 256 KiB, the first naming the destination; the agent's CopyOut chunks are 256 KiB already. An Exec request can't outgrow it in practice: Linux refuses a command line and environment much larger than 2 MiB (`E2BIG`).
- **No lock spans jobs in Create or Start (PROTO-16).** The job table's lock is held only to look a job up or change the table; each job's own lock serialises its calls, as the protocol recommends. So Creates and Starts of different jobs run in parallel, and one slow pull or boot holds up only its own job.

### Stopping: the drain

- **SIGTERM and SIGINT both start a drain: the plugin takes no new jobs, serves the jobs it has until each is removed, then exits.** forgejo-runner dials a new connection for every job and refuses the plugin unless its health check says `SERVING`, and nothing in the runner retries a refused job; so exiting at once and draining cost a new job the same, and only draining lets the plugin be restarted or upgraded alone without killing running jobs. SIGINT behaves like SIGTERM so a terminal and a service manager agree.
- **During a drain, health turns `NOT_SERVING`, the listen socket stays open, and a new Create fails with `Unavailable` `runner-microvm is shutting down`,** before any check of its request. Keeping the socket open gives a new job a clear status instead of "connection refused". `Unavailable` is reserved for this case (#54): the runner reads it as "the plugin is gone". Create checks the drain first, and again as it adds the job to the table, under the table's lock, so no job enters the table once the drain has begun.
- **A Create still waiting for a disk or the memory budget also fails with `Unavailable`.** It has no VM yet, and waiting through a drain would hold the plugin up for a job that hasn't started. The wait is #10's, and must end with the drain once it exists.
- **Every job that already has an environment id is served as usual until it is removed: Start, Exec, CopyIn, CopyOut, Remove, and the environment-timeout backstop.** That is what a drain is for.
- **The plugin exits 0 once its job table is empty and no removal is still tearing a job down.** It then kills nothing, since nothing is left, and releases its locks as on any exit. Serving stops gracefully: the calls still in flight, such as the last Remove, send their answers, for at most 1 s, since by then every one of them fails or answers at once, and a health `Watch`, which never ends by itself, must not hold the plugin up.
- **A second SIGTERM or SIGINT ends the drain at once: serving stops, every job is removed as Remove does (its job process killed, its host files deleted), and the plugin exits 0.** A Remove already tearing its job down when serving stops finishes first: stopping serving doesn't wait for it, so the plugin does. The operator asked for it twice. A clean exit leaves nothing behind; startup cleanup is for crashes. The signals are read in order from a channel that queues two, so one sent while the first is being handled is never lost; two sent at the same instant can reach the plugin as one, since the kernel holds one pending signal of a kind.
- **No drain timeout of the plugin's own.** The service manager's stop timeout and its SIGKILL bound the drain, and the liveness pipe makes the VMs die with the plugin then (VM-6).
- **SIGHUP keeps reloading during a drain (CFG-7).** A reload changes later jobs only, and there are none, so it is harmless, and one signal handler stays simple.
- **A SIGTERM or SIGINT during startup stops the plugin before it binds the listen socket,** since it has no job to drain. `serve` takes both signals at once, before it reads the config file.
- **Health reports `SERVING` from the moment the socket is bound until the drain begins, then `NOT_SERVING`, for both the overall service `""` (which the runner checks) and the BackendPlugin service, `plugin.v1alpha.BackendPlugin`.** The socket is bound only after startup cleanup, writing the binaries and the check of libkrun and libkrunfw, so a client never sees a starting plugin and there is no "starting" status to report. (Flagged decision, #94: the ticket names the service `runner.plugin.v1alpha.BackendPlugin`, but the proto's package is `plugin.v1alpha`, so that is the name a client checking the service by its gRPC name asks for. Rejected reporting under the ticket's name, which no client derives from the service.)

### The scratch disk

- **The job process creates each VM's scratch disk in `<state>/jobs/<id>/<n>/`, before it starts the VM child: a sparse file of the VM's scratch size, mode 0600.** Its size is apparent, so the file grows only as the guest writes. The job spec already says the job process creates it, and it is the job's file, deleted with the job's state directory at Remove.
- **It is formatted with the host's `mkfs.ext4 -q -F -E lazy_itable_init=1,lazy_journal_init=1,root_owner=0:0`,** which takes about 50 ms and allocates about 4 MB. The plugin looks `mkfs.ext4` up on `PATH` at startup, stops with an error naming it when it is missing, and passes its path in the job spec, so the job process runs the binary startup checked. This makes e2fsprogs a host dependency (`docs/development.md`). Formatting in the guest would need a mkfs the image may not have, or an ext4 writer of our own; an embedded template would need `resize2fs` for each profile's size anyway.
- **The file must not exist yet, and a disk that can't be made is deleted.** A failure is a `Failed` event naming the scratch disk (PROTO-10). A fresh file for each VM is why nothing written in one job is visible in the next (VM-5).
- **It is the VM's first block device, `/dev/vda`, read-write.** It is not locked: no other process ever names it.
- **Its size is the job's profile's `scratch_gib`, 10 GiB by default** (Configuration, below).

## libkrun

- **libkrun is bound with purego, not cgo, and only the job binary loads it: the VM child, and `libs`, the VM child's own loading run once at startup (below).** With cgo, libkrun is linked when the binary loads, so `lib_dir` (VM-10) would need `LD_LIBRARY_PATH` and a missing library couldn't give a clean error. purego `dlopen`s from the named directory, and the libkrun 1.x calls take only ints and strings. See [ADR 0004](adr/0004-libkrun-via-purego.md).
- **The libraries are `libkrun.so.1` and `libkrunfw.so.5`, and the code targets the libkrun 1.x API.** These are the sonames of the minimum versions.
- **They load from the system by soname, through the system's dynamic loader, or, with the plugin-level key `lib_dir` set, only from that directory, with no fallback to the system** (Configuration, below). A mistyped directory must fail, not silently load another libkrun. From `lib_dir`, the VM child opens `libkrunfw.so.5` first, then `libkrun.so.1`, whose own need of `libkrunfw.so.5` is then met by the one already loaded. `lib_dir` is absolute, as every path key is, because the VM child changes its working directory before it loads libkrun.
- **At startup, after writing the job binary and before binding the listen socket, the plugin runs the job binary once with `libs`, or `libs <lib_dir>`.** Only the VM child may load libkrun, so the plugin process never does. A plugin that says `SERVING` and then fails every Start is worse than one that won't start: a service manager notices only the second. (Flagged decision, #95: `lib_dir` is `libs`'s one optional argument, and `libs` answers with one `<soname>=<file>` line per library on stdout, exit 0, or its error on stderr, exit 1; the plugin keeps at most 64 KiB of each. Rejected passing the directory in an environment variable, since the plugin reads none but `RUNNER_MICROVM_CONFIG` and an argument shows in the process list, and JSON output, which two lines of paths don't need.)
  - `libs` loads both libraries exactly as the VM child does, requires every libkrun function the VM child calls, and `krunfw_get_kernel` in libkrunfw, the function libkrun loads it for, and prints the files the dynamic loader picked, one `<soname>=<file>` line each. Every missing function is named, not only the first. From `lib_dir` it also checks that the `libkrunfw.so.5` libkrun loaded is the directory's, so a file there with another soname can't let libkrun take one from the system. (Flagged decision, #95: the check opens `libkrunfw.so.5` by soname with `RTLD_NOLOAD` after libkrun is loaded and compares its handle with the directory's, and `libs` requires `krunfw_get_kernel` in libkrunfw. Rejected trusting the file name in the directory, which lets a libkrunfw with another soname send libkrun to the system's, and checking only libkrun's functions, which lets any library under libkrunfw's name pass and fail every VM.)
  - The plugin logs both files, as the loader names them (symlinks unresolved), and `lib_dir`, before it serves.
  - Any failure, a timeout of 30 s included, stops startup with `libs`'s error, which names the missing library or functions and where they were to load from: the directory, or by soname. (Flagged decision, #95: 30 s. Rejected no timeout, which lets a library on a stalled network mount hang startup until the service manager's own timeout, and a few seconds, which a cold page cache on slow storage can exceed: loading two libraries takes milliseconds.)
  - `libs`, as the `version` run before it, leads a process group of its own, and the plugin kills the whole group at the timeout, so nothing it started outlives it. It gets `Pdeathsig` `SIGKILL` from a thread locked until it is reaped, so it dies with the plugin. A SIGINT or SIGTERM to the plugin during `libs` ends it and stops the plugin before serving, as at any other point of startup; a terminal's SIGINT to the plugin's process group never reaches `libs` itself.
- **By soname, the VM child opens `libkrun.so.1` first, then `libkrunfw.so.5` by soname, which returns the one libkrun's own need picked,** found through libkrun's run path or the system's; so the file logged is the one in use. (Flagged decision, #95: by soname the VM child opens libkrunfw too, after libkrun, and both files come from `dlinfo(RTLD_DI_LINKMAP)` of each handle. Rejected opening libkrunfw first, as from `lib_dir`, which searches the system's path instead of libkrun's run path and so can load another file than libkrun would, and opening only libkrun and reading libkrunfw's file from `/proc/self/maps`, which is parsing where one more `dlopen` returns the loaded library's handle.)
- **libkrun's log level is the plugin-level key `libkrun_log_level`: `warn`, `info`, `debug` or `trace`, built-in `warn`, read at startup only** (Configuration, below). It is separate from the plugin's own log level, because libkrun's `debug` is a flood of virtio traffic nobody wants with the plugin's own debug lines. It never goes below `warn`, so libkrun's errors always reach the VM log. The plugin passes it in the job spec, the job process passes it on in each VM child's spec, since the VM child is the only place libkrun runs, and the VM child sets it with `krun_set_log_level` (libkrun's 2 to 5) before any other call; any other value fails the VM before libkrun is called. (Flagged decision, #95: the level travels as a string, field 7 of the job spec and 15 of the VM child's, under the config's own names, which the VM child maps to libkrun's numbers. Rejected a proto enum, whose required zero value is a fifth case every reader must handle, and libkrun's number, which puts libkrun's scale in the plugin and the job process.)
- **No version check in code.** libkrun 1.x has no version function, and libkrunfw's `krunfw_get_version` returns only its major version (`5` for 5.3.0, 5.5.0 and 5.6.4 alike), so a check could only read file names, a heuristic that says nothing on an unversioned name. The minimums are libkrun 1.19.8 or later, built with block and network support, because libkrun #949 truncates disk images before it, and libkrunfw 5.6.4 or later, the version proven by the prototype. They are stated here for #12's operator documentation, and stay enforced where the project builds them: `just check-libs` and the flake's checks (`docs/development.md`).
- **Every binary builds with `CGO_ENABLED=0`.**

## Job network

Every job gets its own private job network, run inside its job process, and its VMs reach the outside through it (NET-1, NET-2, NET-3, NET-5). A step can resolve names through the gateway and open TCP connections to anything the host can reach except the host's loopback and link-local addresses, and those connections leave the host as the job process's own, under the plugin's user. The network ends with the job process: at Remove, or when the plugin dies.

- **The job network is gvisor-tap-vsock, run inside the job process.** Its stack isn't freed on `Close`, which is harmless because the job process ends with the job. The alternatives, passt and slirp4netns, are separate C binaries, which breaks the single-binary decision.
- **It is the library's `virtualnetwork.New`, configured only: no NAT table, no gateway virtual IPs, no port forwards, no DNS zones, link-local access off.** It is the library's whole switch, gateway, DNS and forwarders with no code of ours (but the guard, below). The loopback mapping and the extra virtual IP are only `gvproxy`'s command-line defaults, so leaving them out is what makes NET-4 hold. Building the stack ourselves to drop its DHCP server would copy about 40 unexported lines we would then track upstream. Its HTTP API is never served: nothing calls its handler.
- **Its DHCP server runs but no VM uses it, and `DHCPStaticLeases` reserves each VM's address for its MAC.** `virtualnetwork.New` always starts it and no setting turns it off. Nothing in the guest asks it (no VM runs a DHCP client, below), and a step that runs one gets its own VM's address back, so the server can't hand one VM's address to another (NET-6: the gateway serves DNS to the guest, and a DHCP server no VM uses whose leases are fixed by the plugin; nothing it serves exposes host ports or the host's loopback).
- **Link-local addresses (`169.254.0.0/16`) are refused** (the library's `Ec2MetadataAccess` off, its default). On a cloud host a job could otherwise read the instance's credentials from the metadata service (NET-5: the plugin filters none of the guest's connections, except that link-local addresses are unreachable).
- **ICMP echo to the outside is forwarded** (the library's handler), within the guard's bound, below; an echo to the gateway is answered by the guard. `ping` is a common step diagnostic and costs no code. It goes out through an unprivileged ping socket, so a host whose `net.ipv4.ping_group_range` excludes the plugin's user drops it; #12's operator docs say so.
- **The library's logger (logrus's standard one) passes only its errors on, through the job process's own logger to the job process log file, at most 10 at once and one a second after that, counting what it drops; logrus's own output is discarded.** A guest can make the library log a line per packet, and the job process log file has no cap. Once the job network closes, it drops the switch's error for each port's read that the close ended: every normal teardown would otherwise log one per VM. With `golang.org/x/time/rate` for the bound, already in the module graph.
- **Names the gateway's DNS can't answer from a zone go to the host's resolver** (there are no zones), from inside the job process. A loopback name server on the host (systemd-resolved, Docker's embedded DNS in the harness) therefore works, though the guest can't reach the host's loopback itself.
- **IPv4 only:** no IPv6 address in the guest beyond loopback's `::1`, and no AAAA filtering. gvisor-tap-vsock has no IPv6. The agent sets `eth0`'s IPv6 address generation mode to none before bringing it up, through rtnetlink since `/proc/sys` need not be mounted, so the kernel gives it no `fe80::` address either. With no IPv6 route a connect to an AAAA address fails at once, and clients fall back to IPv4; filtering AAAA would be our own code in the DNS path.
- **Each VM's switch port is guarded: of the frames a VM sends the gateway, only those to an outside unicast address reach the forwarders, and to the gateway itself only its DNS and DHCP.** The library's forwarders dial or send to each packet's destination from the host, so a TCP connection to any gateway port but 53 would otherwise leave the host for whatever has the gateway's address on the host's networks, and hang until the forwarder's 30-second connect timeout; and a packet to `0.0.0.0`, which a host dial or send takes as its own loopback, would reach the host's loopback (NET-4: the gateway's stack drops loopback destinations arriving on its link, but hands UDP to `0.0.0.0` to its forwarder). So the guard drops every packet, of any protocol, to `0.0.0.0/8`, `127.0.0.0/8`, multicast (`224.0.0.0/4`) and `240.0.0.0/4` with the limited broadcast in it, but DHCP (UDP 67) to the limited broadcast, where a DHCP client sends. To the subnet it passes only the gateway's DNS (UDP and TCP 53) and its DHCP server (UDP 67); it answers a TCP connection to any other gateway port with a reset, as a host with nothing listening does, and an echo request to the gateway with an echo reply of its own, because the library's ICMP forwarder hands every echo request it sees to a host ping socket, the gateway's address included, so the stack's own reply would come with a ping of `198.18.0.1` out of the host's default route. It drops every other packet to a subnet address and every frame too short to have an Ethernet header, which the switch would otherwise read past. Of ICMP to the outside it passes only unfragmented echo requests, at most 10 at once and 10 a second after that per VM, a bound it shares with its echo replies: the library logs every other ICMP packet, and answers each echo request with a goroutine and a host ping socket held up to 5 seconds for the reply, so a VM holds at most 60 of each, and a flood's excess is dropped. A rate rather than a cap on those in flight, because the guard can't see when the library's wait for a reply ends. It drops every frame whose source isn't the VM's own MAC, so `Attach` takes the VM's MAC: the library's switch learns every source MAC and forgets one only when its port goes away, so random source MACs would grow the job process without bound. Frames between VMs (to a VM's MAC) and ARP pass unchanged. (Flagged decision, #62: the ticket expected the library's configuration alone to make every gateway port but 53 refuse, and its test showed it doesn't. Rejected: a NAT entry mapping the gateway to an address the host refuses at once, which depends on the host kernel's answer and would be one typo from the host's loopback; a short connect timeout, which would also cut short every real slow connect.)

### Addressing

- **Subnet `198.18.0.0/24`, fixed, with no config key.** Every job network can use one subnet, because each is its own switch. A real host inside the subnet can't be reached from a job, and RFC 2544's benchmarking range never appears on a real LAN, unlike gvisor-tap-vsock's default `192.168.127.0/24` or CGNAT's `100.64/10` (Tailscale). A key can be added if a collision is ever reported.
- **The gateway (and DNS) is `.1`; the VM at index *n* in the job spec is `.(2+n)`, so the job's container is `198.18.0.2`. MACs are locally administered and derived from the address: `02:00` and the address's four bytes (the job's container `02:00:c6:12:00:02`, the gateway `02:00:c6:12:00:01`).** The plugin computes both when it builds the job spec, with no allocator, so a later VM needs no change to the job network. It caps a job at 253 VMs.
- **The guest has an ordinary `/24` with a default route via the gateway, not a `/32`.** It is the simplest shape, it lets VMs of one job reach each other later, and the gateway answers ARP for no unused address, so a connection to one never leaves through the forwarder.
- **Static addressing by the agent, from the boot config, with no DHCP client in the guest.** libkrun init's DHCP client takes the first reply within 100 ms with no retry, and checks neither the transaction id nor the client MAC, so VMs booting together on one network can take each other's addresses, and one slow reply leaves a VM with no address and no error.

### The VM's link

- **A `SOCK_DGRAM` socketpair, one Ethernet frame per datagram (vfkit framing), served by the switch; the VM's end is the VM child's fd 4, attached with libkrun's `krun_add_net_unixgram` with no path, the VM's MAC, no features and flags 0** (no DHCP client, no vfkit handshake). Proven by the spike. Flags 0 means libkrun's init never runs its DHCP client. The job process closes its copy of the VM's end once the VM child has started, so the switch's writes fail, rather than fill the socket, once the VM child is gone.
- **Both ends get 1 MiB send and 4 MiB receive buffers; MTU 1500.** Proven by the spike. The kernel caps each at its `wmem_max` and `rmem_max`. Throughput tuning (a larger MTU) is a follow-up only once a problem is measured.
- **libkrun's implicit vsock and transparent socket impersonation stay off; the only vsock port is the agent's.** With TSI on, guest sockets become host sockets, loopback included, bypassing NET-4 and NET-6.

### In the job process

- **It starts the job network before any VM child, sends `NetworkUp`, then starts the VMs.** A VM must never boot before its switch serves its socket. A network that fails to start sends `Failed` with the reason `network: <err>`, which Start reports as `FailedPrecondition`.
- **The job network attaches VMs one call per VM socket, not a constructor wired to one VM.** It costs nothing today and a second VM needs no refactor. The job process still rejects a spec with other than one VM. Closing the network closes every switch port and waits until each port's goroutine has returned.

### In the guest

- **The agent configures the guest's network with `github.com/vishvananda/netlink`, on the agent's dependency allow-list:** `lo` up (explicitly, not trusting libkrun's init), then on `eth0` the address, MTU, IPv6 address generation off and up, then the default route via the gateway, once the root is built and before it listens. A maintained library instead of our own rtnetlink code. A failure fails the boot, naming the step, so Start fails with the VM's console tail.
- **IPv4 forwarding is left at the kernel's default (off).** The plugin does nothing for a specific workload; a job that needs it (dockerd's nftables backend) sets it as root.

### Hostname and name resolution

A step sees the hostname and name resolution it expects (GST-12): the hostname is the job's name made DNS-safe, it resolves to the VM's own address, `localhost` resolves, and every other name resolves through the gateway.

- **The hostname is the runner's `CreateRequest.name`, lower-cased (ASCII), each run of characters outside `a-z0-9-` replaced by `-`, leading and trailing `-` trimmed, cut to 63 characters, any `-` left at the cut trimmed again, and `job` when nothing remains.** The runner's name is unique per job and readable (task, workflow, job), which tells a step more than the environment id; 63 is a DNS label's limit, and the second trim keeps a cut name valid. The plugin computes it at Create.
- **One function makes every VM name DNS-safe (`internal/plugin`'s `dnsName`).** The job's container's name is this hostname; a service's name will be its workflow key through the same function, so the rule can't drift.
- **No DNS zone and no search domain; names on the job network live in each VM's `/etc/hosts`.** A search domain costs every outside lookup an extra round trip, bare names for services would need a zone and a search domain both, and `/etc/hosts` works for every resolver a step uses (glibc, musl, Go, Node).
- **The boot config carries the hostname and a list of hosts, each a name and an address, which the agent writes into `/etc/hosts`.** Today it holds one entry, the VM's own name at its job-network address; services later add entries without a new field.
- **The agent writes the three files once the network is up, then sets the kernel's hostname (`sethostname`), before it listens:**
  - `/etc/hosts`: `127.0.0.1 localhost`, `::1 localhost`, then one line per hosts-list entry. The hostname maps to the VM's own job-network address, not `127.0.1.1`, so tools that resolve their own hostname (`hostname -f`, Java, sudo) get the address others would reach them on.
  - `/etc/hostname`: the hostname and a newline. `/etc/resolv.conf`: one line, `nameserver <gateway>`.
- **They are written into the job's root, so onto the scratch disk's writable layer: each a regular file, mode 0644, owned by root, whatever the image has there.** Writing into the root is the least code; Docker-style bind mounts from a tmpfs gain nothing here. The agent writes each through an `os.Root` on the job's root, to a temporary file beside it (`O_EXCL`), sets its owner, then its mode, and renames it into place. So a symlink there, Ubuntu's `resolv.conf` → systemd-resolved included, is replaced rather than followed, a dangling one too, and its target is untouched. A missing `/etc` is created, root-owned, 0755. Anything that stops a write (a directory at `/etc/hosts`, a file at `/etc`, an `/etc` that is an absolute symlink such as `/etc` → `/usr/etc`) fails the boot, naming the file, and leaves no temporary file. The absolute symlink fails because `os.Root` refuses it, naming `/etc`: no symlink may lead out of the job's root.
- **The agent refuses a hostname or a host that isn't a DNS label at an IPv4 address,** so nothing in the boot config can add a line of its own to `/etc/hosts`.

### Room for services

Nothing below is built; it is written down so the services epic starts from decisions:

- addresses and MACs come from the VM's index (Addressing, above);
- every VM's `/etc/hosts` lists all the job's VMs (the boot config's hosts list, above);
- a service's name on the job network is its workflow key, made DNS-safe by the hostname's rule; two VMs whose names map to one name fail at Create;
- a service's `ports:` never become host ports (NET-3): they become forwards inside the job's container, from its loopback to the service, in the agent, so workflows written for `localhost:<port>` work;
- the job network never reads where a VM's shape comes from (a profile or the job spec).

## Extracting the job binary and agent

- **The plugin writes the job binary to `<state>/bin/runner-microvm-job-<first 12 hex of its sha256>`, and the agent to `<state>/bin/runner-microvm-agent-<first 12 hex of its sha256>`.** The state directory is less often `noexec` than `/run`. The content hash makes upgrades clean: once both are written, every other file in `<state>/bin/` (stale hashes, a crashed write's temp files) is deleted, since the plugin holds every directory lock.
- **It always rewrites both at startup, even when a file of that name exists:** a temp file in `<state>/bin/`, fsync, rename, then fsync of `<state>/bin/`. A file is never trusted by its name: a power loss after a rename without those fsyncs can leave an empty file under the right name, and `version` would then fail with a misleading error.
- **At startup the plugin runs the extracted job binary once, with `version`.** If that fails, startup stops with an error naming the directory and its config key. There is no fallback: a `memfd` exec can be blocked by sysctl hardening, and it is more code. It then runs it with `libs`, which checks libkrun and libkrunfw (libkrun, above).
- **The agent is written once per plugin, and each VM's boot root holds a hard link to it, not a copy** (The boot root, below). The state directory is one filesystem, so the link always works.

### The embedded payload

- **The embedded payload is a build-time guarantee.** One file in `internal/payload`, behind the `payload` build tag, embeds the job binary and the agent by exact file name, so a missing binary is a compile error.
- **Without the tag, a stub returns `ErrNoPayload`,** so plain `go build`, `go vet`, `go test` and lint work without building the payload first.
- **Release and `kvm` builds pass `-tags payload`.**
- **`just build` always builds the job binary and the agent first, with `-trimpath -buildvcs=false`,** so the plugin binary is reproducible under Nix.
- **The built payload is not committed.**

## The boot root and the guest's root

[ADR 0005](adr/0005-image-layers-are-erofs-files-on-one-virtiofs-share.md) records why the guest's root is built this way.

- **Each VM boots from its own small boot root, `<state>/jobs/<id>/<n>/root/`, which libkrun shares read-only as the VM's root** (`krun_add_virtiofs3` with the root tag `/dev/root`). It holds empty `proc`, `sys` and `dev` mount points, so libkrun's init can mount them and images without them boot (GST-2). It also holds the agent, as a hard link, and the agent's boot config. It is the bottom layer of the guest's root, so the agent and its config stay visible in the job's root.
- **libkrun's init stays PID 1 and starts the agent as its workload.** It already sets up the console and the guest's start; replacing it gains nothing the agent needs.
- **The agent is `/.runner-microvm/agent` and its boot config `/.runner-microvm/boot-config.binpb`, both in the boot root.** One hidden directory keeps the job's root tidy and names both after the program. The agent is the hard link to the agent written at startup, the boot config a file written per VM, mode 0600 on the host.
- **The boot config is the agent protocol's `BootConfig` message, encoded as binary protobuf.** It is already a protobuf message, and the agent already links protobuf; a second encoding adds nothing.
- **The boot config carries the image's defaults for Exec: the image config's environment, `USER` and `WORKDIR`, which the image cache hands Start with the layers, and the plugin's default `PATH`.** The boot config is how the agent learns anything about its VM, and the plugin already returns the same default `PATH` to the runner as `default_path_variable`, so both use one value.
- **Both stay visible in the job's root filesystem.** The boot root is the overlay's bottom layer, and the boot config holds nothing a step can't read anyway, such as the image's environment.
- **The agent's environment is empty, passed explicitly to libkrun, never NULL.** With NULL, libkrun passes the host's environment into the guest; the agent looks nothing up in `PATH`, and every step gets its environment from its Exec.
- **The VM gets two read-only virtiofs shares of its own: its boot root as its root, and its layer link directory, under the tag `layers`, which the agent mounts at `/dev/.runner-microvm/layers`.** The profile's mounts add one share each (below). Read-only is enforced on the host by libkrun's flag, so the guest can't write a layer even after remounting the share read-write (IMG-9). Each VM can read only its own image's layers, because its share is its own link directory (IMG-8). The layers take one share, not one device each: libkrun allows 3 mounts plus disks per VM on x86_64, which rules out a block device per layer, and flattening the image would lose sharing between images.
- **The layer share's tag and mount point are values only the plugin sets, as the vsock port is.** The plugin puts the tag in the job spec, for libkrun's share, and both in the boot config, for the agent's mount, so the share and the mount can't name two tags; the agent and the VM child refuse an empty tag. The tag `layers` names what the share holds, and needs only differ from the root's `/dev/root`. The mount point is under the agent's staging directory, beside the scratch disk and the layers' mounts, because the devtmpfs is the one writable place before the root exists. (Flagged decision, #53: rejected keeping the tag as two constants, the agent's and the VM child's, which only a booted VM's test catches parting, and making the mount point the agent's own constant, which would drop a boot config field for no gain: it is already one value in one place.)
- **The agent builds the root at boot,** in `/dev/.runner-microvm/`, because devtmpfs is the one writable place before the root exists:
  1. It mounts the scratch disk (ext4).
  2. It mounts the layer share read-only, at the boot config's `layer_dir`.
  3. It mounts each layer file as a file-backed EROFS (`source=` the file, no loop device). This needs `EROFS_FS_BACKED_BY_FILE`, which libkrunfw 5.6.4 has.
  4. It builds an overlay with `fsopen` and one `lowerdir+` per layer, top layer first, with the boot root (the VM's `/` at boot) at the bottom. `upperdir` and `workdir` go on the scratch disk. Overlay's stacking limit, 500, covers GST-3's 120 layers, and the image cache refuses an image of more than 499. `lowerdir+` needs kernel 6.8 or later; libkrunfw 5.6.4 is 6.12. Unlike `mount(2)`'s option string, it has no page-size limit on the layer list.
  5. It makes its mounts in the new root, creating each mount point in the overlay if the image lacks it: `proc`, `sysfs` and `cgroup2`, `nosuid,nodev,noexec`; `devtmpfs` on `/dev`, `nosuid`; `devpts`, `nosuid,noexec,gid=5,mode=620,ptmxmode=666`; a `tmpfs` on `/dev/shm`, `nosuid,nodev,noexec`. They are what container engines give a container, so images and steps find what they expect. A mount failure fails the boot, naming the mount.
  6. It creates the act path, tool cache and temp directory (PROTO-7) that the image lacks, below.
  7. It makes the profile's scratch paths in the new root (GST-13), below.
  8. It creates the act path, tool cache and temp directory again, so one a scratch path covers is made on the scratch disk, below.
  9. It mounts the profile's mounts and disks at their targets (STO-1, STO-4, STO-6), below.
  10. It moves the overlay to `/` and chroots. The boot root, the shares and the layers stay mounted beneath it, out of the job's reach.

  The layer list, the scratch device, the directories, the scratch paths, the mounts and the disks come from the boot config. The agent's new mount API calls are raw system calls, because the agent may not import `golang.org/x/sys`.
- **The act path, tool cache and temp directory are created only when the image lacks them, and an existing one is left as it is:** a directory of its own mode, a file. A created `/tmp` gets mode 1777, set explicitly so the umask can't drop the sticky bit; a created `/var/run/act` and `/opt/hostedtoolcache` get 0777, root-owned, and any missing parent 0755. Any user a step runs as must be able to write them. Something above one that is not a directory fails the boot, naming both.
  - **Each is resolved inside the job's root, with that root as the boundary, as a scratch path is,** so an image's `/var/run` → `/run` puts the act path at `/run/act`, never on the agent's own filesystem, and `..` never climbs out. **A symlink to nothing is followed, inside the root, and its target created with its missing parents,** so `/var/run` → `/run` works on an image without `/run` too; a relative target is taken from where the link's directory really is, and a chain of more than 40 links fails the boot. The agent walks the path a part at a time, each part looked up from the root with `openat2`'s `RESOLVE_IN_ROOT`, and reads a missing part as a link with `readlinkat`, since `openat2` reports only that the target is missing.
  - **One that lands in `/proc`, `/sys` or `/dev`, or would be created there, through a symlink in the image, fails the boot, naming where it lands,** as a scratch path does, so no image makes the agent create a cgroup or write into the devtmpfs that holds its staging directory. An existing one there fails too, though nothing would be made, so the rule is the scratch paths' rule. The agent checks where each directory it reaches really is, not `RESOLVE_NO_XDEV`: after the scratch paths are bound, a directory under one is on another mount, and must be made there.
  - **They are made twice: before the scratch paths and after them.** The first pass puts them in the overlay, so a scratch path on one, such as `/tmp`, takes its mode, 1777, even when the image lacks it. The second makes again one that a scratch path at or above it, such as `/var/run`, `/var` or `/opt`, hid under its fresh, empty directory, so it is on the scratch disk; everywhere else the first pass's directory is there and left alone. (Flagged decision, #53: rejected making them only after the scratch paths, which gives a scratch path on `/tmp` 0755 where the image lacks `/tmp`, and refusing a scratch path at or above one in the config, which forbids a reasonable profile.)
  - **The boot config lists them, each with its mode, and the plugin fills the list from the paths Create returns.** So the paths are set in one place, as the vsock port is, and making them configurable later through profiles changes only the plugin. (Flagged decision, #53: rejected the agent's own constants, which would be a second copy of Create's paths that must agree.)
- **Each scratch path is a fresh, empty directory on the scratch disk, bind-mounted over the path, hiding whatever the image has there.** Seeding it with the image's contents would mean a copy at every boot, on the Start path, and the use scratch paths exist for, dockerd's `/var/lib/docker`, whose overlay2 driver can't use an overlay upper, wants an empty directory anyway. A fresh scratch disk for each VM makes each one empty at every boot.
  - **The agent resolves each path inside the job's root, with that root as the boundary** (`openat2` with `RESOLVE_IN_ROOT`), so an absolute symlink in the image, such as `/var/run` → `/run`, lands at its target in the image, never on the agent's own filesystem, and `..` never climbs out. It bind-mounts onto the directory it resolved, by descriptor (`open_tree` and `move_mount`).
  - **It resolves every scratch path before it binds any,** recording where each lands (symlinks resolved) and the image's owner and mode there. A nested path's image directory is hidden once the path above it is bound, so resolving it afterwards would see only the fresh, empty parent. At bind time it looks up each landing place again inside the root, creating it in a fresh parent above it if it has to.
  - **If the image has the directory, the fresh one gets its owner and mode. Otherwise the agent creates the path, with any missing parents, root-owned, mode 0755,** and the fresh directory takes that. Modes are set explicitly, after the owner, so neither the umask nor the chown drops a bit such as `/tmp`'s sticky bit. A directory between two nested scratch paths that is not itself listed is 0755 in the fresh parent.
  - **Something on the path that exists but is not a directory, a symlink to a file or a symlink to nothing included, fails the boot, naming the path,** so Start fails with the VM's console tail (PROTO-10, VM-8).
  - **A path that lands in `/proc`, `/sys` or `/dev`, or under them, through a symlink in the image, fails the boot the same way.** The config refuses those paths as written; the agent refuses them where they land. It resolves with `RESOLVE_NO_XDEV`, so no path crosses from the overlay onto any mount, which at that point are the agent's own mounts, and it also checks each landing place against the three. Binding over one would hide the kernel's files. Two paths that land in the same place fail too: the second would hide the first.
  - **The order is: after the overlay root and the agent's own mounts; then the scratch paths, parents first by where they land (a path after every listed path whose landing place is above its own, else in the list's order); then the profile's mounts and disks, together, in the list's order, mounts before disks, since none may land under another (below) (STO-6).** Ordering by landing place, not by the listed path, keeps a symlink in the image from binding a parent over a child already bound. The act path, tool cache and temp directory are made both before and after the scratch paths, above.
  - **Each path's directory on the scratch disk is `paths/<i>`, named by its position in the list, never by the path,** so no guest path can name a file outside its directory on the disk. The upper and work directories sit beside them.
  - Today the list applies only to the job's container, because the plugin protocol passes no VM options for services.
- **Each of the profile's mounts is a host directory shared into the VM as a virtiofs share of its own, read-only unless the entry sets `read_write: true` (STO-1, STO-2, STO-3).** Today the list applies only to the job's container, because the plugin protocol passes no workflow mounts or volumes, and no VM options for services (STO-11).
  - **The VM child adds each with `krun_add_virtiofs3`, after the layer share, with `read_only` set unless the entry is read-write, and no DAX window (`shm_size` 0).** libkrun's server then refuses every write with EROFS, even after the guest remounts the share read-write or mounts the tag again elsewhere (STO-2), as for the root and layer shares. **A read-write mount is the same share with `read_only` off, and the agent mounts it without `ro`, still `nosuid,nodev`;** nothing else about it differs (#89).
  - **The tag is `mount<i>`, `i` being the entry's position in the profile's `mounts`, never derived from the path.** libkrun copies a tag into a 36-byte buffer with no length check, and panics when the VM starts on a longer one; the VM child refuses an empty tag or one over 36 bytes. The plugin sets the tag in the job spec, for libkrun, and with the target in the boot config, for the agent, so the two can't part, as the layer share's.
  - **The job process checks each source again before it makes the scratch disk and starts the VM child: one that is missing or no longer a directory fails Start with `mount <source>: does not exist` or `mount <source>: is not a directory` (PROTO-10).** A source can disappear after the config was read, and libkrun would report it only as `-EINVAL` at boot. Checking before the scratch disk saves an mkfs on a job that can't start.
  - **The agent mounts each as `virtiofs` with `nosuid,nodev`, plus `ro` unless the entry is read-write, by descriptor (`fsopen`, `fsmount` with those mount attributes, and `move_mount` onto the target's descriptor).** A host directory's files carry host owners and modes, and the guest shouldn't gain privilege from them.
  - **The owner of a file the guest writes on a read-write mount is libkrun's behaviour, documented, not changed (STO-3, #89).** With the plugin unprivileged, a file the guest's root creates there is owned by the plugin's user. A guest user with any other uid can't create files there, unless it has the plugin user's uid, and `chown` fails: where the host directory's mode bars that uid, the guest's kernel refuses it with EACCES ("Permission denied"), and where the mode allows it, libkrun does with EPERM ("Operation not permitted"). With the plugin as root, files get the guest's uid and gid, and `chown` works. libkrun's Linux virtiofs server switches its thread to the guest's uid and gid when it has `CAP_SETUID` and `CAP_SETGID`, and otherwise creates files as itself, refusing other uids; it keeps no ownership xattr, and its C API offers no setting for this. Making every write the plugin user's would need the VM child in a user namespace, privileged setup at odds with VM-9 and with #1's "no subordinate ids"; patching libkrun is ruled out, since the project never depends on an upstream change. #9's exit check, files "owned by the plugin's user", is the unprivileged plugin with a root step, which is what the harness runs.
  - **Operator warning: a read-write mount's host directory can receive setuid files and, with the plugin as root, device nodes; mount its source `nosuid,nodev` on the host, or keep it where no other user reaches it.** The guest's `nosuid,nodev` protect only the guest; libkrun's server passes the guest's `chmod` and `mknod` on to the host as they are. With the plugin unprivileged, a guest root's `chmod 6755` on a file there leaves a setuid and setgid file owned by the plugin's user on the host, and `mknod` of a block or character device fails with EPERM ("Operation not permitted"), as the host refuses the plugin's user. With the plugin as root, the same `chmod` leaves a setuid-root file (a copy of `/bin/sh` is a root shell for whoever can run it), and `mknod` succeeds: a guest root can leave `/dev/sda`'s block device (8:0), mode 0666 and root's, in the host directory. The tests check both (Tests, below). (Flagged decision, #89 review: the plugin neither strips these bits nor refuses `mknod`, since libkrun's virtiofs server does the writes and its C API offers no setting to intercept them. Rejected: patching libkrun, which the project never depends on, and refusing read-write mounts when the plugin runs as root, which takes away STO-3's guest-owned files for the case where the host's own mount options already fix it.)
  - **Each target is resolved inside the job's root, with the root as the boundary, as a scratch path is (`openat2` with `RESOLVE_IN_ROOT`, a part at a time, the walk the act path, tool cache and temp directory use).** An absolute symlink in the image then lands inside the image, never on the agent's own filesystem. Unlike a scratch path it crosses mounts, so a target under a scratch path lands on that path's fresh directory on the scratch disk. A target missing from the image is created in the overlay, with any missing parents, root-owned, mode 0755; a symlink to nothing is followed, inside the root, and its target created, as for the act path. A non-directory in the image at the target, or above it, fails the boot, naming it, so Start fails with the console tail (PROTO-10, VM-8). A target that lands in `/proc`, `/sys` or `/dev`, at the root, where another target lands, or at or above where a scratch path or the act path, tool cache or temp directory landed fails the boot the same way, naming both, before any mount is made: the config refuses those as written (Configuration, below), and only an image's symlinks, such as `/var/run` → `/run` with a target `/run`, can make one land there. (Flagged decision, #88: rejected refusing a symlink to nothing, as a scratch path does: the ticket asks for missing targets to be created, and following the link inside the root, as the act path does, can't leave it.)
  - **The agent resolves every target before it mounts any, then mounts them in the list's order. A target that lands under or above where another target lands fails the boot, naming both, before any mount is made (STO-6).** The config refuses a target under another as written; only an image's symlinks can make two land nested, such as `/data` → `/srv/x` with targets `/srv` and `/data`, and then the inner one's mount point would be made in the host directory mounted at the outer one, through virtiofs, in the operator's storage. (Rejected mounting them parents first, the scratch paths' rule: it makes that mount point.) At mount time the agent looks each landing place up again inside the root, and fails the boot, naming both, when it lands anywhere else, so a symlink inside a host directory, such as `sub` → `/`, can never move the mount past the checks above.
- **Each of the profile's disks is a host file attached to the VM as a block device, mounted at its target, read-only unless the entry is read-write (STO-1, STO-2, STO-4).** A read-write disk gives a job a writable ext4 filesystem that persists in the host file. Today the list applies only to the job's container, because the plugin protocol passes no workflow mounts or volumes, and no VM options for services (STO-11).
  - **The job process opens each disk's source before it makes the scratch disk and starts the VM child, read-only for a read-only disk, and holds the files until the VM child has exited. A source that is missing or not a regular file fails Start with `disk <source>: does not exist` or `disk <source>: is not a regular file` (PROTO-10).** The open never blocks, so a FIFO put at the source fails at once instead of hanging the job; the file's type is checked on the open file, not the path. The VM child inherits the files as fd 5 and up, in the order of `disks`.
  - **Every disk takes a disk lock on the file the job process opened, as soon as it is open and checked, before the scratch disk is made: `flock(LOCK_EX|LOCK_NB)` for a read-write disk, `flock(LOCK_SH|LOCK_NB)` for a read-only one (STO-7, STO-8, #91).** Two VMs can never write one disk, and no VM reads a disk another VM is writing: a reader seeing another VM's writes in flight is the same corruption STO-7 exists to prevent, so read-only disks are locked too, and any number of readers share one. The job process holds the locks until the VM child has exited, and the kernel releases them if either dies (Ending a job, above). Its files are close-on-exec, so mkfs never holds a lock; only the VM child, which is handed them, does. A child being started holds a copy of every open file of its parent from fork until exec closes the close-on-exec ones, so a lock outlives its last close while its process is starting a child. The job process never does then: it closes its disks when one fails to lock, before mkfs runs, or once the VM child has exited, and only it opens them, so a freed disk is free to the next job at once.
  - **A lock already held fails Start with `disk <source> is in use by another process`, the same text whether this job wanted to read or to write,** so STO-7's wording stays true in both directions. Until #10 (Queueing), both directions fail at once rather than wait; #10's queue must make readers and writers wait for each other, with readers sharing. Since no lock waits, the order a job's disks are locked in can't deadlock two jobs; a disk that fails closes the ones locked before it, which releases them.
  - **The VM child adds each disk with `krun_add_disk`, after the scratch disk, path `/proc/self/fd/<n>` and `read_only` set, so the file libkrun opens is the very file the job process opened and locked.** libkrun reopens a disk by its path inside `krun_start_enter`, and itself takes no lock; the descriptor's path stops a source replaced after the job process's check from being the file attached. With `read_only` set, libkrun's device is read-only, so the guest can't write the disk even after `mount -o remount,rw`, which its kernel refuses (STO-2).
  - **Each disk's block id is `disk<i>`, `i` being its position in `disks`, never derived from the path.** libkrun gives the guest the block id as the virtio-blk serial, up to 20 bytes, in `/sys/block/<dev>/serial`; the VM child refuses an empty id, one over 20 bytes, and the scratch disk's id, `scratch`, which it keeps. The plugin sets the id in the job spec, for libkrun, and with the target in the boot config, for the agent, so the two can't part, as a mount's tag.
  - **The agent finds each disk by its serial, reading `/sys/block/*/serial` in the job's root's sysfs, never by its position as `/dev/vdb`, `/dev/vdc`, ….** The serial is libkrun's documented identity for a disk, so a change in device order can't mount the wrong disk. A disk whose serial no device has, or two have, fails the boot, naming its target. It finds and probes every disk before it resolves any target, so a bad disk fails before anything is created.
  - **The agent reads each disk's superblock magic and mounts the filesystem it names: ext4 (`0xEF53` at byte 1080) or EROFS (`0xE0F5E1E2` at byte 1024, checked first). Anything else fails the boot with `disk <target>: not ext4 or EROFS`.** This gives one clear error instead of two mount errors.
  - **A read-only ext4 disk whose journal needs recovery (`needs_recovery`, `s_feature_incompat` bit `0x4`) fails the boot with `disk <target>: its ext4 journal needs recovery, which a read-only mount can't do: mount the disk read-write once to replay it`.** It is never mounted with `noload`, which would silently show a half-written filesystem. The flush (The flush, above) leaves disks clean after a normal job, so only a crash leaves one dirty (STO-10). **A read-write disk must be ext4: any other filesystem fails the boot with `disk <target>: read-write disks must be ext4`,** since ext4 is what the guest kernel can write and replay after a kill (#91). One needing recovery is mounted, and the mount replays its journal. A read-only disk may be ext4 or EROFS.
  - **The agent mounts each disk `ro`, its superblock read-only too, with the kernel's default `relatime`, and neither `nosuid` nor `nodev`, by descriptor as it mounts a share (`fsopen` with `source` the device and the `ro` flag, `fsmount`, `move_mount` onto the target's descriptor).** A disk is a whole filesystem the operator hands over for workloads such as a container store, whose images hold setuid binaries, and the VM is the security boundary. A read-only superblock is needed besides: the kernel refuses a read-write one on a read-only device.
  - **Targets are resolved, created and checked exactly as mounts' are,** in one list with the mounts, so a disk and a mount landing at one place, or one under the other, fail the boot, naming both, as two mounts do.
- **A failure to build the root ends the agent, so the VM exits during boot,** and Start fails with its console tail (VM-8).

## Exec

The agent runs each step's command as a workflow author expects of a container (GST-4 to GST-7, GST-9). Its defaults come from the boot config's image defaults (The boot root, above).

- **Exec's environment is the image's, with the request's on top.** The runner already layers the image's environment under each step's, so for steps this changes nothing; it gives the runner's own Execs, which carry no image environment, the behaviour of `docker exec`. An image entry without `=` names no variable and is dropped, from StartComplete's image environment as from Exec's.
- **The command is looked up in that environment's `PATH`, or in the default `PATH` when it sets none, and is never run through a shell (GST-4).** The environment then gets the default `PATH` too, as a container engine gives one, so the command and what it starts look in the same places.
- **Exec runs as the request's user, else the image's `USER`, else root (GST-5).** That's what container engines do.
- **Users resolve with `github.com/moby/sys/user`, against the image's `/etc/passwd` and `/etc/group`, by runc's rules:** names, numeric ids, `user:group`, supplementary groups; a numeric uid with no passwd entry gets gid 0; root gets its supplementary groups; an explicit group replaces the user's own and its supplementary groups. An image without the files runs as root or a numeric id. It's small, Apache-2.0, has no dependencies of its own beyond `golang.org/x/sys`, and is maintained by the moby project; parsing passwd and group files ourselves is the bug-prone code the project avoids owning. It is on the agent's dependency allow-list.
- **`HOME` defaults to the user's home, and to `/` for a user with no passwd entry or no home in it,** as container engines do. An environment that sets `HOME` keeps its own.
- **The agent changes ids only when they differ from its own.** In a VM it is root and takes any user's; that the same ids need no change also lets its tests run on the host unprivileged, where only those that change ids need root.
- **Exec runs in the request's working directory, else the image's `WORKDIR`, else `/` (GST-6).** As container engines do. A relative one is an exec failure: the plugin has already taken a step's from the job's workspace (The plugin server's calls, above), and no other base is one the runner and the agent agree on.
- **A missing working directory is created, with its missing parents, mode 0755, owned by the user the command runs as; an existing directory is never re-owned.** A step running as a non-root user must be able to write its own working directory, and re-owning an image's directory would change the image. Something on the path that is not a directory is an exec failure. The agent walks the path from an open parent and re-owns each directory it made through its own descriptor, never following one it made: a step's background process can swap that directory for a symlink, and a chown or chmod by path would then land on the symlink's target. A symlink the image has on the path is followed.
- **Output is streamed as it is written. After the command exits, everything it wrote is sent, then the stream ends at most 200 ms later, even while a background child keeps its output open (GST-9).** 200 ms catches output still in flight without making a step wait on a daemon it started.
- **The exit code is the command's, or `128+n` for signal `n`; a command that can't start (missing executable, unknown user or group, a working directory that can't be made) is an exec failure, not an exit code (GST-7).** The runner shows the two differently.
- **There is no stdin and no TTY.** The plugin protocol carries none.

## Copying files

The agent's CopyIn and CopyOut move files in and out of the job's container intact (GST-10, GST-11), as the runner's Docker backend does.

- **Copies use the standard library's `archive/tar`, with every path in CopyIn resolved through an `os.Root` at the destination.** `os.Root` refuses any path or link that leaves the destination, enforced by the kernel, which removes the bug-prone part of extracting a tar safely. `moby/go-archive` would bring many modules into the agent, whose dependencies are an allow-list.
- **CopyIn creates the destination and its missing parents, mode 0755, also for an empty archive, and an entry's missing parents the same way.**
- **CopyIn keeps each entry's mode, set-id and sticky bits included, its owner, its times and its extended attributes.** That's what the runner's Docker backend gives a job, and the runner copies its own tools and actions in this way. An entry with no access time gets its modification time as one.
  - **The owner is set first, then the mode, then the extended attributes, then the times, each explicitly,** since a change of owner clears the set-id bits and file capabilities, and so the umask never narrows a mode. A regular file's are set through its own descriptor; a symlink's through its parent's, opened in the root, never following the symlink.
  - **The owner is changed only when it differs from the header's.** In the VM the agent is root and takes any owner; on the host its tests run unprivileged, and those that change owners run only as root.
  - **A directory's mode and times are set once the whole archive is written, deepest first.** Writing into a directory changes its modification time, and a read-only directory must still take what the archive puts in it.
  - **Each directory is reached for that from the destination one component at a time, following no symlink (`openat` with `O_NOFOLLOW` and `O_DIRECTORY`), and one no longer reachable that way is skipped.** A later entry can replace a symlink on the directory's path; its mode and times must then land on no other directory, and the copy must not fail after everything was written. Only the destination's and the current component's descriptors are held, never one per directory.
  - **A CopyIn that fails partway still sets the modes and times of the directories it made so far, best effort, and returns its own error.** Otherwise they stay at 0700, the mode they are made with so they can take their contents.
  - **An extended attribute the kernel refuses as unsupported or not permitted is skipped, and the CopyIn logs one `warn` line with their count and the first refusal.** Docker skips them too: a filesystem without them, or a `trusted.` attribute without the privilege, says nothing about the files.
- **CopyIn never replaces a directory with a non-directory, and no entry or hard-link target lands outside the destination,** through `..`, an absolute name, or a symlink in the archive or already at the destination; such an archive fails with `InvalidArgument`, having written nothing outside. **An absolute entry name or hard-link target, or one whose `..` takes it out of the destination once cleaned (`../x`, `a/../../b`), is refused before anything of that entry is written,** rather than cut back into the destination as `tar` and Docker cut a leading `/`: an archive that names a path outside means something else, and writing it elsewhere, or linking to the destination's own file of that name, would put the wrong file in place. A name whose `..` stays inside (`a/../b`) is the path it cleans to, as Docker takes it. (Flagged decision, #56 review: rejected refusing every `..`, which refuses archives Docker takes, and keeping the cut-back names, which the ticket's criterion refuses.) Any other existing entry is replaced. A hard link takes its target's metadata, since they share one inode.
- **Absolute symlinks: one on the destination's own path, above it or at it, is followed; one inside the destination on an entry's way is refused, even when it points inside the destination.** The destination is opened as a plain path, which the job's root resolves (the agent is chrooted into it), so `/var/run` → `/run` puts a copy into `/var/run/act` at `/run/act`, as Docker does. Inside the destination every path goes through the `os.Root`, which takes any absolute link as leaving it: an entry under an absolute symlink the archive made, or one the destination already held, fails the CopyIn with `InvalidArgument`, writing nothing there. An absolute symlink entry itself is written with its target as it is, and an existing symlink an entry names is replaced, never followed. Relative symlinks inside the destination are followed while they stay inside it. (Flagged decision, #56 review: kept the refusal. Rejected resolving absolute links against the job's root, as Docker does inside the container's root: the agent's root is the job's, so that would let an archive's link write anywhere in the job's root, which the rule above refuses. Rejected resolving them against the destination, as `RESOLVE_IN_ROOT` there would: `/dest/real` would land at `/dest/dest/real`, where neither Docker nor the link points. The runner's archives, each a directory's tar, hold no entry under a symlink of their own, so only a destination that already holds an absolute symlink where a copy brings a directory is affected.)
- **CopyIn reads the stream to its end after the archive's end-of-archive marker, and discards the rest, before it answers.** GNU tar and bsdtar pad an archive to a whole record (10 KiB by default) after the marker, the runner sends all of it, and an answer before the runner's last send fails that send with "stream closed unexpectedly". Docker discards what follows the marker too. The read lasts only as long as the call: Remove cancels it. The plugin's relay needs nothing of its own: it reads the runner's stream to its end unless the agent's call has already ended, and then the runner reads the agent's status (`CloseAndRecv`) after its failed send.
- **CopyIn takes regular files, directories, symlinks and hard links, and skips a PAX global header, which describes no entry** (git archive writes one with the commit). Any other entry type fails the CopyIn: the runner sends none.
- **CopyOut returns the path as a tar with entries named relative to its parent, hard links and extended attributes kept (GST-11).** The runner reads `GITHUB_ENV`, `GITHUB_OUTPUT` and `GITHUB_STATE` back this way, and a local action's files; artifacts need files intact.
  - **A regular file reached again through another of its hard links, by device and inode, is written as a hard link to the first name;** each entry's extended attributes go in its PAX records (`SCHILY.xattr.<name>`), as GNU tar and Docker write them.
  - **Times are kept to the second, with no access or change time,** as Docker's archives do: reading the files would change them anyway.
  - **A socket, which a tar can't hold, is left out.**
  - **An extended attribute whose name holds `=`, which Linux allows and a PAX record's key can't, is left out, and the CopyOut logs one `warn` line with their count and the first.** Failing the whole copy for one attribute would lose the files, and it matches CopyIn's skip of attributes the kernel refuses.
- **A CopyOut that the guest's files fail, by a permission or I/O error reading them or a file cut short while it is copied, fails with `FailedPrecondition`; one whose send fails keeps the stream's own code; any other failure is `Internal`.** The guest's files are the job's, and a step can change them while they are copied; `Internal` is for the agent's own bugs, such as a tar it writes wrongly.
- **CopyOut sends 256 KiB chunks, never more.** It's the runner's own chunk size, well under the agent's 4 MiB message limit.
- **A missing path returns an empty tar: two zero blocks, 1024 bytes.** The runner parses a missing env file as empty.

## Configuration

The plugin's settings and its profiles come from the config file, one YAML file (CFG-1). `internal/config` reads and validates it; the plugin is its only user.

- **`runner-microvm serve` runs the plugin, and `runner-microvm check` validates the config file and exits 0 if it is valid, or 1 after printing every error.** Neither takes arguments; no subcommand, an unknown one or an argument prints the usage and exits 2. With `check`, an operator tests a file before a reload or a restart instead of reading the log afterwards, and one way to name the file keeps `serve`, `check` and reload in agreement.
- **The file is `/etc/runner-microvm/config.yaml`, unless `RUNNER_MICROVM_CONFIG=<path>` names another;** a relative path in the variable is made absolute once, at startup. It is the default path plus the override that operators and packagers expect.
- **No file at the default path means every setting takes its built-in value, and the plugin logs that it found none; so does an empty file (CFG-1). A missing file that `RUNNER_MICROVM_CONFIG` names stops startup, and so does any file that exists but can't be read, including a symlink at the default path, or on the way to it, whose target is gone.** A typo in the variable never falls back to built-in values without a word.
- **`RUNNER_MICROVM_CONFIG` is the plugin's only environment variable for an operator setting; every other one is a key in the file.** One source of truth means `check` validates everything, and the startup log prints the whole effective config: at startup the plugin logs the file it read, or that it found none, and every plugin-level setting in effect. Kept logs become a key with #11's child that builds them.
- **The file is decoded with `go.yaml.in/yaml/v3`** (the YAML organisation's maintained fork, MIT and Apache-2.0). It is maintained and gives line numbers; `sigs.k8s.io/yaml` loses them, and `goccy/go-yaml` adds a dependency for no gain.
- **The decoder walks the file's `yaml.Node` tree itself, key by key, so every error, decoding and validation alike, carries the line of the key at fault and, inside `profiles`, the profile's name:** `config <path>: line <n>: profile "<name>": <key>: <problem>`, and for a plugin-level key the same without the profile (CFG-2, CFG-3). An unknown key fails exactly as `KnownFields` would, but `KnownFields` exists only on a `yaml.Decoder` over bytes, not on a node's `Decode`, so a profile decoded from its own node couldn't use it, and its errors would be the library's text, whose line would have to be parsed out. Walking the nodes never blames a key written after `profiles:` on the last profile. Every error in the file is reported, not only the first. A key set twice in one mapping fails, naming both lines.
- **A YAML syntax error stops startup with the library's line.** A second YAML document in the file is an error, and a top level that isn't a mapping is too.
- **Unknown top-level keys are errors, Compose-style `x-` keys included.** Operators share values between profiles with YAML anchors on a profile and merge keys (`big: {<<: *default, cpus: 8}`): plain YAML, which the decoder expands, so the plugin never sees it, and profiles still don't inherit from each other (CFG-5). An explicit key wins over a merged one; an error in a merged key names the line where it is written and the profile it was merged into. A mapping that merges itself fails, and merges that expand to more than 100,000 keys fail, so a file can't make decoding loop or blow up.
- **The plugin-level keys are read at startup only; a reload changes none of them (below):**

  | Key | Built-in value | Rule |
  |---|---|---|
  | `listen` | `unix:///run/runner-microvm/runner-microvm.sock` | `unix://` followed by an absolute path; any other form is an invalid value |
  | `state_dir` | `/var/lib/runner-microvm` | absolute |
  | `cache_dir` | `/var/cache/runner-microvm` | absolute |
  | `runtime_dir` | `/run/runner-microvm/jobs` | absolute |
  | `max_memory_mib` | unset | an integer ≥ 0; unset or 0 means no limit (Admission, below) |
  | `cache_max_gib` | 20 | an integer ≥ 0 whose byte count fits an `int64` (at most 8589934591): the image cache takes its cap as an `int64` of bytes; 0 keeps no layer that no VM is using (Image cache, below) |
  | `lib_dir` | unset | absolute; unset loads libkrun and libkrunfw by soname through the system's dynamic loader, set loads them only from it (libkrun, above) |
  | `libkrun_log_level` | `warn` | `warn`, `info`, `debug` or `trace`: libkrun's log level in every VM's log (libkrun, above) |
  | `log_level` | `info` | `debug`, `info`, `warn` or `error`: the log level of the plugin, every job process, every VM child and every agent (Logging, below) |

  - The names end in `_dir`: that says what the value is, and avoids a bare `cache` in a file operators keep next to the runner config, whose own `cache:` section is the actions cache.
  - `listen` keeps the `unix://` scheme: it matches the runner's `plugins.<key>.address`, and leaves room for another transport later without changing the key.
  - Every path must be absolute, or startup stops naming the key: a relative path would depend on whatever working directory the service manager uses. Paths are cleaned.
  - A key with no value (`state_dir:`) is an invalid value, as is a value of the wrong type, such as a quoted number.
  - The directories must follow the rule in Failure handling and startup cleanup (below); the check is `internal/config`'s, part of loading the file, so `check` runs it too and `serve` runs it before any directory lock is taken. It only reads: missing directories are created at startup, as before.
  - `max_memory_mib` is read, validated and kept for #10, which builds the admission behind it.
  - A plugin-level 0 is taken literally, except `max_memory_mib`, where 0 means no limit: literal values are honest.
  - `cache_max_gib` is converted to bytes and passed to the image cache's constructor as its size cap (IMG-14); there is no `cache_max_mib`, because tests set a small cap on the constructor directly. A value whose byte count overflows an `int64` is invalid, as for `scratch_gib`, rather than clamped: a clamped value would be logged as typed but not be the cap in effect. `cache_max_gib: 0` is taken literally: plugin-level 0 is literal, and here it is a meaningful value, a cache that keeps nothing no VM is using.
- **`profiles` is a map from profile name to profile.** A name must match `[a-z0-9][a-z0-9_-]*`: a name with `;`, `=`, a space, or an empty name can never appear in a label, so it's a mistake best caught at load. Each profile key arrives with the change that gives it meaning.
- **The profile keys:**

  | Key | Built-in value | Rule |
  |---|---|---|
  | `cpus` | 2 | an integer, 1 to 255 |
  | `memory_mib` | 1024 | an integer, 1 to 4294967295 |
  | `scratch_gib` | 10 | an integer ≥ 1 whose byte size fits an `int64` (at most 8589934591): the scratch file's size is an `int64` of bytes |
  | `scratch_paths` | `[]` | a list of guest paths, each absolute, not `/`, not `/proc`, `/sys` or `/dev` or under them, and listed once (GST-13) |
  | `mounts` | `[]` | a list of `{source, target, read_write}`: `source` an absolute path to an existing directory, `target` a guest path under STO-5's rules, `read_write` `false` by default, `true` for a read-write mount (STO-1, STO-3, STO-5) |
  | `force_pull` | `false` | `true` or `false` (IMG-6) |

  - The scratch size key is `scratch_gib`, not `disk_gib`: `disk_gib` would sit next to #9's `disks:` list, which means something else.
  - A key left out takes its built-in value; `0` is an invalid value that stops startup (CFG-3). Having `cpus: 0` silently mean 2 is magic, and the decoder can tell a missing key from a 0. So is a negative value, a quoted number, or no value.
  - The only upper bounds are the ones that can't work (CFG-10): `cpus` above 255 (libkrun's one-byte field), `memory_mib` above what libkrun's `uint32` of MiB holds, and on amd64 more than 3 mounts plus disks in a profile (below). There is no minimum memory and no scratch cap: a VM too small to boot fails Start with its console tail (PROTO-10).
  - When `max_memory_mib` is set, a profile the file defines whose `memory_mib`, its own or the built-in value, is more than it stops startup, naming both values: no job on that profile could ever run, so the operator finds out at load. The implicit `default` (below) isn't checked, since the file doesn't define it; nothing refuses a job on it yet, and #10's admission check will refuse it at Create (Admission, below). (Flagged decision; rejected: failing startup for `max_memory_mib` below the built-in 1024 when no `default` is defined, which would refuse a file whose labels all name small profiles.)
  - `scratch_paths` lists the guest directories that live on the scratch disk instead of the overlay, each empty at every boot (The boot root and the guest's root, below). The name settles #1's placeholder. Each path is cleaned, so `/a/./b/` and `/a/b` are the same path, listed twice. Its target rules are STO-5's, so operators learn one set; nested paths (`/a` and `/a/b`) are allowed. An invalid path fails at its own line, naming the key and the profile, and every invalid path in the list is reported. A path with a NUL byte is invalid: no guest path can hold one. A scratch path equal to or under a mount or disk target in the same profile fails too (below); a mount or disk under a scratch path stays allowed (STO-6).
  - `mounts` lists the host directories shared into the job's container, each at its `target` (STO-1). The names are plain, and settle #1's prototype choice. Each entry is decoded strictly from its own node, as the rest of the profile is, so an unknown key, or an entry without a `source` or a `target`, stops startup, and every error names the line, the key and the profile: `line <n>: profile "<name>": mounts: <key>: <problem>`. Every invalid entry is reported. Today only the operator's profiles name mounts, because the plugin protocol passes no workflow mounts or volumes (STO-11).
  - **A mount's `read_write: true` makes it read-write; `false`, the built-in value, keeps it read-only (STO-2, STO-3).** Only YAML's plain `true` and `false` are valid, as for `force_pull`. A read-write mount follows every other rule here unchanged.
  - **A source must be an absolute path to an existing directory, or a symlink to one, checked when the file is read (STO-5),** so a typo fails at once, as everything else in the config does, and a reload fails on a source that is gone and keeps the old config (CFG-8). It is cleaned. The job process checks it again at Start (The boot root and the guest's root, above).
  - `disks` lists the host files attached to the job's container as block devices, each mounted at its `target` (STO-1, STO-4). Its entries have the same keys, `source`, `target` and `read_write`, are decoded and reported the same way, `line <n>: profile "<name>": disks: <key>: <problem>`, and its built-in value is `[]`. Today only the operator's profiles name disks, because the plugin protocol passes no workflow mounts or volumes (STO-11).
  - **A disk's source must be an absolute path to an existing regular file, or a symlink to one, checked when the file is read (STO-5),** as a mount's is, and cleaned. A directory, a missing file and a character device stop startup; **so does a block device, with `is a block device: a disk's source must be a regular file`.** Block devices can be allowed later by adding a rule. The job process opens each source at Start (The boot root and the guest's root, above).
  - **A disk's `read_write: true` makes it read-write; `false`, the built-in value, keeps it read-only (STO-2, STO-4).** Only YAML's plain `true` and `false` are valid, as for a mount.
  - **A disk source listed twice in one profile, where either entry is read-write, stops startup at the later entry's `source`, with `"<source>" is the same file as the source on line <n>: a disk listed twice must be read-only both times` (#91).** One process can't hold an exclusive `flock` and a shared or second exclusive one on one file through two opens, and a profile is today the only way a job gets two entries; the Create-time rule for one job (One job process runs all of a job's VMs, above) stays, for services. Two entries are one file when their cleaned paths match or, through a symlink or a hard link, they are the same inode, which is what a `flock` locks. Two read-only entries for one file load: two shared locks don't block each other.
  - **The target checks, which mounts and disks share:** a target is cleaned, follows the scratch paths' rules (absolute, not `/`, not `/proc`, `/sys` or `/dev` or under them, no NUL byte), and may be used only once across `mounts` and `disks`. **A target equal to one of the same profile's `scratch_paths`, or above one, stops startup,** since one would hide the other; one under a scratch path is allowed and is mounted after it (STO-6, #8's grilling). **So does a target equal to or above one of the guest's own directories, the act path `/var/run/act`, the tool cache `/opt/hostedtoolcache` and the temp directory `/tmp` (PROTO-7),** so `/var`, `/opt` and `/tmp` are refused and `/opt/tools` or `/opt/hostedtoolcache/go` are not. The agent makes those directories before the mounts, and a mount at or above one would hide it from every step. The paths are constants in `internal/config`, which the plugin returns from Create and sends in the boot config, so the list can't part from what the agent makes. (Flagged decision, #88: a mount is made after the scratch paths and the guest's directories, so one at or above them silently hides them, the reason the ticket gives for refusing nested targets. Rejected: allowing it and documenting the hiding, which leaves a job broken with no error; mounting before the scratch paths, which contradicts STO-6.) **A target equal to or under another mount or disk target in the same profile stops startup,** reported on the inner one: otherwise the agent would create a mount point inside an operator's host directory, or fail on a read-only one. Nesting can be allowed later by adding rules, not changing these.
  - **Mounts plus disks: at most 3 per profile on amd64; more stops startup at the line of the later of `mounts` and `disks`, with the count, the limit and why (CFG-10).** libkrun 1.19.8 on x86_64 gives virtio-mmio devices 11 interrupt lines (IRQs 5 to 15), and every VM already uses 8: the console, the balloon, the rng, the root share, the layer share, the scratch disk, the network and vsock. libkrun's own failure is a bare `-EINVAL` from inside `krun_start_enter`, with the reason only in its log. The limit is a constant in `internal/config` beside a comment listing the 8 devices, so a device removed raises it. On arm64 there is no check: its 128 lines are far beyond any profile, and arm64 isn't supported. Entries count whether or not they are valid, so the limit's error doesn't wait on the others.
  - `force_pull: true` makes every Start of a job on the profile look its tag up in the registry, even when the image cache holds it; a registry error then fails the Start (IMG-6). The job's profile copy, taken at Create, decides it, like every other profile value, and Start passes it in `imagecache.Request.ForcePull`. It is `false` by default, as in Docker: a tag resolves once and is kept until it is evicted, so `force_pull` is how an operator gets fresh images. Only YAML's plain `true` and `false` are valid: a quoted value, a number, `yes` or no value is an invalid value.
  - Profiles never inherit from each other, `default` included (CFG-5): each is the built-in values plus its own keys. A profile with no keys (`name:` or `name: {}`) is all built-in values.
- **The profile is chosen at Create, from the label (CFG-4, CFG-6).** A label with no `;profile=` uses the profile named `default`; if the file defines none, the built-in values. A label that names `profile=default` when no `default` is defined gets the built-in values too: `default` always exists, implicitly. A label naming any other profile the file doesn't define fails Create with `InvalidArgument`: `label "<label argument>": unknown profile "<name>"`. Create's log line names the profile and its values, and startup logs every profile, `default` always among them.
- **The job keeps a copy of its profile, taken at Create, for its whole life.** A reload never changes a job already created, even one not yet started (CFG-7). The job spec's VM gets the copy's `cpus`, `memory_mib` and scratch size in bytes (VM-4, VM-5) and its mounts' sources, tags and read-write flags, its boot config the copy's `scratch_paths` (GST-13) and its mounts' tags, targets and read-write flags (STO-1, STO-3), and its image's `Acquire` the copy's `force_pull` (IMG-6). The copy's lists are its own, so nothing a reload swaps can reach them.
- **A reload happens on SIGHUP, and only on SIGHUP (CFG-7).** SIGHUP is what `systemctl reload` sends; watching the file would catch editors' half-written saves. `serve` takes SIGHUP before it reads the config file, so a SIGHUP during startup never ends the plugin, and one that arrives then is handled once the server exists. Reloads run one at a time, in one goroutine that `serve` stops as it exits, without waiting for a reload still reading the file: that reload finds the server closed and changes nothing, logging so. Signals that arrive during a reload make one more.
- **A reload reads the same absolute path that startup resolved, under the same rules:** no file at the default path means built-in profiles, and a missing file named by `RUNNER_MICROVM_CONFIG`, or an unreadable file, is a failed reload. `RUNNER_MICROVM_CONFIG` is not read again: a process's environment can't change.
- **The config file must be a regular file, at startup and on reload; anything else is an unreadable file.** It is opened without blocking and checked before it is read, so a FIFO with no writer or a device can't hang a reload. A stalled network mount can still block the read, but not the plugin's exit: `serve` doesn't wait for that reload, so a drain that ends, or a second SIGTERM, still ends the plugin and frees its directory locks.
- **Only `profiles` reload. A plugin-level key whose value in the file differs from the running one is logged by name, with both values, as needing a restart, and the running value stays.** Directories, the listen socket and caps belong to running state that can't be swapped safely mid-flight.
- **A reload validates the whole file, as startup does, and checks its profiles against the running plugin-level values:** a profile is checked against the `max_memory_mib` in effect, not a new value the file sets but a restart hasn't applied.
- **A failed reload (an unreadable file, a YAML error, or any validation error) keeps the old config entirely, and logs the error with the same line, key and profile as at startup (CFG-8).** Applying half a file would leave profiles nobody wrote.
- **A successful reload replaces the profiles in one step (`Server.SetProfiles`), and logs each profile as startup does, then the profile names it now has, last, so a reader that sees that line has the whole reload.** A Create in flight sees either the old set or the new one, never a mix: it copies its profile under the same mutex. A reload never reaches into a created job (above).
- **The label is `<runner label>:<plugins key>://[//]<image>[;profile=<name>]`.** The runner passes the plugin what follows `<plugins key>:`, less a leading `//`.
  - The plugin strips one more leading `//`, then splits at the first `;`. OCI references can't contain `;`, so the split is safe.
  - After the `;`, only `profile=<name>` is allowed. Each of these fails Create with `InvalidArgument`, naming the label argument: an empty name, any other key, a second key, and a trailing `;`. The runner reserves `InvalidArgument` for malformed requests (#6). Matching is exact and case-sensitive.
  - An empty image part (`runner-microvm://;profile=big`) is valid: it means the job brings its own `container:` image. A job with no image in either place fails Create with `InvalidArgument` (PROTO-5). This lets operators offer a VM shape without forcing an image.
  - Create checks, in order: services (refused, PROTO-6), the label's form, its profile, then the image. So a malformed label or an unknown profile fails even when the job has a `container:` image.
- **A job's `container:` image replaces the label's image; the label's profile still applies (PROTO-4).** The image is the workflow's choice, and the VM's shape is the operator's. Create records the chosen image, and Start acquires it.
- **A Create that can't work fails at once, with a code the runner understands and a message the job log shows:**
  - no image in either place, or a malformed label argument: `InvalidArgument` (PROTO-5), because the runner reserves it for a malformed request. An unknown profile is `InvalidArgument` too (above).
  - a job that declares services: `Unimplemented`, with `runner-microvm does not run services: the plugin protocol passes no options to configure a service's VM` (PROTO-6). The request is well formed; the plugin can't do it yet, which is what `Unimplemented` means. Services return when the protocol carries per-service options.
- **Create returns fixed paths: root `/`, act path `/var/run/act`, tool cache `/opt/hostedtoolcache`, temp `/tmp` (PROTO-7).** Nothing asks for them to change; making them configurable can come later through profiles.
- **Create also returns `default_path_variable`, the plugin's default `PATH`: `/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin`.** The runner uses it for a job whose image sets no `PATH`, and Start puts it in the boot config as the agent's default `PATH` (The boot root, below), so the runner and the agent use one value, owned by the plugin. `path_variable_name` and `path_separator` are left unset, so the runner uses `PATH` and `:`.
- **Create returns `os` `Linux` and an `arch` that follows the host: `X64` on amd64, `ARM64` on arm64.** It is the runner's `RUNNER_ARCH`, and images resolve for the host's platform. The plugin refuses to start on any other architecture, naming it, before it writes anything, because libkrun supports only those two. Only amd64 is tested and supported (#5).
- **`backend_options`, `cap_add` and `cap_drop` are ignored. The first Create in a plugin process that carries any of them logs one warning naming which (`fields=`, comma-separated), whether or not that Create succeeds; no later Create warns again.** `backend_options` is the runner config's `plugins.<key>.options` map, the same for every job, and the plugin's own config file already covers what it would hold. `cap_add` and `cap_drop` are set only by the `forgejo-runner exec` command's flags, never by the runner daemon or a workflow; steps run as root with every capability in a VM of their own. Honouring `cap_drop` later only adds an Exec field.

## On-disk layout

`<state>`, `<cache>` and `<runtime>` are the plugin's directories, and `<listen>` is the directory holding its listen socket; each has its own config key (CFG-9). `<id>` is the job's environment id, and `<n>` is the VM's index in the job spec's VMs: 0 for the job's container, then each service in order. Today the job's container is the only VM, because the plugin protocol passes no VM options for services. A VM's directories are named by its index, never by its name, because the workflow chooses a service's name (One job process runs all of a job's VMs, above). Each VM gets its own directories, so a job's VMs never share a file by accident; the job process log is the job's, so it stays at the job's level.

| Path | Holds |
|---|---|
| `<state>/lock`, `<cache>/lock`, `<runtime>/lock`, `<listen>/lock` | the directory locks |
| `<state>/bin/` | the job binary and the agent |
| `<state>/jobs/<id>/` | the job process log |
| `<state>/jobs/<id>/<n>/` | the VM's scratch disk, VM log and console |
| `<state>/jobs/<id>/<n>/root/` | the VM's boot root: `proc`, `sys` and `dev` mount points, and `.runner-microvm/` holding `agent`, a hard link to the agent, and `boot-config.binpb`, the boot config |
| `<state>/logs/<id>/` | kept logs (whether to keep them is #11's) |
| `<runtime>/<id>/<n>/` | the VM's agent socket |
| `<listen>/` | the listen socket, mode 0660 |
| `<cache>/layers/<diffID hex>.erofs` | one EROFS file per layer, shared by every image and VM that uses it; its mtime is its last use |
| `<cache>/images/<manifest digest hex>.json` | an image's raw config |
| `<cache>/tags/<sha256 hex of the normalised reference>` | a tag file: the normalised reference (a tag, or an index's digest) and the manifest digest it resolved to |
| `<cache>/jobs/<id>/<n>/` | the VM's layer link directory: `0.erofs`, `1.erofs`, …, hard links to its image's layers, bottom first |
| `<cache>/tmp/` | partial writes |

`<state>`, `<cache>` and `<runtime>` are distinct directories, none inside another; `<listen>` is either `<runtime>` or a fourth such directory (see below). `<state>` and `<cache>` are mode 0700. Image cache, below, says why the cache is laid out as it is.

## Image cache

The plugin process pulls and converts images, each layer pull in its own goroutine, and makes and removes each VM's layer link directory, so the job process receives a ready one (#1, Image store).

- **go-containerregistry fetches manifests and layers; go-erofs's `erofs.Create` with continuity's `tarconv.Apply` converts them.** They are maintained libraries, and conversion needs no privilege and no host EROFS support (IMG-4). Both are Apache-2.0. tarconv exists only in unreleased commits, so both are pinned to pseudo-versions, which Renovate updates as digests in its Go group.
- **A layer is converted from its uncompressed stream straight into an uncompressed EROFS file.** No compressed blob is kept: the file is the cache. The image cache decompresses the blob itself, gzip or zstd told apart by its first bytes as go-containerregistry does, in the conversion's own goroutine: go-containerregistry decodes zstd in goroutines of its own, where a panic would end the plugin, so zstd runs with a decoder concurrency of 1, which decodes in the reader's goroutine. The zstd decoder is klauspost/compress's, the one go-containerregistry already depends on, now imported directly. tarconv turns OCI whiteouts into overlay whiteouts (a char device 0:0) and opaque directories into `trusted.overlay.opaque=y`.
- **A layer is named by its diffID, the digest of its uncompressed content: `<cache>/layers/<diffID hex>.erofs`.** The diffID doesn't depend on the registry's compression, so a layer several images share is stored once (IMG-5). The file's presence is the index: there is no index file to keep in sync.
- **The stream is hashed as it converts, and a layer whose content isn't its diffID fails the Start.** The diffID comes from the image config, which the image's author chooses: without the check, an image could name a popular base layer's diffID with other content, and every image using that layer would boot it.
- **The diffID must be a sha256 digest in lowercase hex before it becomes a file name,** and an image may have at most 499 layers: overlay stacks at most 500 lower layers, and the boot root is one of them.
- **Every write goes to `<cache>/tmp/`, then fsync, rename into place, and fsync of `<cache>/layers/`,** the same rule as the job binary. A power loss after a rename without those fsyncs can leave an empty `.erofs` under its real name, which would then count as cached forever. The rename never replaces a file already there (`RENAME_NOREPLACE`): another Start stored the same content first, and VMs may already link it. The cache directory's filesystem must support it (`docs/development.md`); one that doesn't fails each Start that stores a layer, with an error naming the cache directory and the missing support.
- **An image's missing layers all convert before any is renamed into place,** so a layer that fails leaves nothing in the cache, not even the image's other new layers (IMG-10). Every layer is looked up in the cache before any conversion starts, so a lookup that fails starts nothing. The first layer to fail stops that Start's waits on the others, and the Start returns at once; a pull no Start waits on any more is cancelled and deletes its temp file as it unwinds (shared pulls, below).
- **The cache's directories are mode 0700, and its files 0600.** The cache holds image configs, whose environment may carry values. Only the plugin's own user needs access; the same user runs libkrun's virtiofs server.
- **A panic in a layer's decompression or conversion is recovered inside that conversion, and fails only that job's Start (IMG-11).** A pull runs inside the plugin process, so an unrecovered panic would end every job.
- **A layer may hold at most 1,000,000 tar entries and 256 MiB of names, link targets and PAX records (xattrs among them); a layer over either fails that Start with an error naming the limit, and leaves nothing in the cache.** go-erofs keeps every entry's metadata in memory until the layer's file is written, and a layer is untrusted: a small one with millions of entries could exhaust the plugin's memory and end every job. The largest real images hold a few hundred thousand files across all their layers, with paths averaging well under 100 bytes, so both limits are generous. They are counted on a copy of the tar stream as it converts, so the conversion stops at the limit rather than after it.
- **A layer whose uncompressed stream, or EROFS file, is over the cache's size cap fails that Start, naming the cap, and leaves nothing in the cache.** A layer bigger than the cap could never be kept, and a layer is untrusted: a gzip bomb or an endless stream would otherwise fill the cache's filesystem, and the state disk with it when they share one, failing other jobs. Both are counted as the conversion reads and writes, so it stops at the cap rather than after it. The bound is the cap itself, with no limit of its own: anything under the cap can be kept. (Flagged decision: rejected a fixed per-layer limit, which would be one more number to tune and would either refuse real layers or allow a layer the cap can't hold.) **A cap of 0 bounds no conversion:** it keeps no layer that no VM is using, so every layer is over it, yet a VM still needs its layers while it runs; only the cache's filesystem bounds a layer then (below). (Flagged decision, #70: a cap of 0 is a meaningful value, so its Starts must work. Rejected: bounding the conversion by the cap there too, which fails every Start; refusing 0, which the ticket takes literally.)
- **Running out of space mid-conversion fails that Start with an error naming the cache directory, and the temp file is deleted.** Nothing triggers an emergency eviction: the size cap is the operator's tool.
- **The plugin sets no timeout of its own on a stalled pull.** It ends when the job is cancelled or its runner or job timeout expires, as QUE-6 says for every wait; a shared pull ends when its last waiter's cancellation or timeout ends its wait. No memory limit for the plugin is documented.
- **One plugin-wide limit of 3 layer pulls at once.** A limit per image stops being a limit once several cold images pull together. A shared pull takes one place, whatever its number of waiters.
- **A hard link to a file in an earlier layer fails Start with `HardLinkError`, saying the image cache does not support it, and leaves nothing in the cache (IMG-10).** tarconv has no typed error for it, so the image cache matches tarconv's `unresolved hard link "<name>"` text and wraps it in its own typed error; a test pins the text, so a tarconv upgrade that changes the wording fails CI. If tarconv ever gains a typed error, the cache switches to it; the project never depends on that happening.
- **Each VM's layer link directory, `<cache>/jobs/<id>/<n>/`, holds one hard link per layer of its image, named by its position, bottom layer first (`0.erofs`, `1.erofs`, …).** Hard links are what `Image.LinkDir` promises, and they can't cross filesystems, which is why the directory is under the cache. Names come from positions, not diffIDs, because an image may hold the same layer twice. A layer with more than one link is in use. Each layer's mtime is set as it is linked, so it records the layer's last use for eviction (below). A failed Acquire deletes the link directory it began.
- **A layer missing when a Start links it is fetched and converted again, once (IMG-15):** Failure handling and startup cleanup, below, records why.
- **`Release` deletes every link directory of the job, after any in-flight `Acquire` of the same job returns** (Responsibilities and import rules, below), so a job removed mid-pull never leaves a link directory behind (IMG-14). That ends the job's use of its image configs, and then it evicts (below). A cancelled `Acquire` stops waiting on its shared pulls at once, so `Release` never waits for a pull another job shares.
- **A reference is normalised with go-containerregistry's own parser, to its fully qualified name,** so `node:22` and `index.docker.io/library/node:22` are one tag (IMG-1). That's the library's rule, so there is no rule of our own. A reference with both a tag and a digest is its digest.
- **The platform is `linux/<the plugin's GOARCH>`:** a multi-platform index resolves to that image (IMG-2). arm64 isn't refused, but only amd64 is tested in CI and claimed as supported.
- **Credentials come from go-containerregistry's default keychain:** the plugin user's `~/.docker/config.json` (or `$DOCKER_CONFIG`) and its credential helpers (IMG-3).
- **Plain HTTP follows the library's own rule: a registry at a localhost, loopback or RFC 1918 address is tried over HTTPS, then over plain HTTP; every other registry is HTTPS only.** That is a known downgrade on a LAN: someone on the network path to a private-address registry can answer in plain HTTP. It is no code of ours, the in-process test registry needs it, and TLS everywhere would mean a transport of our own overriding the library's. A setting for insecure registries can come with the config file (#8) if anyone asks.
- **An image's raw config is cached as `<cache>/images/<manifest digest hex>.json`, and a tag as `<cache>/tags/<sha256 hex of the normalised reference>`, a JSON object holding the normalised `reference` and the manifest `digest` it resolved to.** A tag file is named by a hash, not the escaped reference, so a long repository path can't outgrow NAME_MAX and no escaping rule is ours; the reference inside it is checked against the one the file is named for, and one that fails the check is damaged (Failure handling and startup cleanup, below). The digest is the platform image's, not the index's. Both are written like layers: a temp file in `<cache>/tmp/`, fsync, rename into place, fsync of the directory, mode 0600 in a 0700 directory.
- **An image config may be at most 8 MiB; a larger one fails that Start.** A config is held in memory and kept in `<cache>/images/`, and the registry is untrusted. Real configs are a few KiB to a few hundred KiB, so 8 MiB is generous; configs count against the cache's size cap (Eviction and pruning, below), so many large ones can't fill the disk. It is refused by the size its manifest declares, before it is fetched, and the read stops past the limit whatever the registry sends.
- **A tag resolves once and is kept until its config is evicted or pruned; there is no tag expiry (#1).** A cached tag whose config is cached is used with no registry request (IMG-6). A tag whose config is gone is looked up again.
- **The digest of a multi-platform index resolves once too, through a tag file of its own** (the normalised `repository@digest`, naming its platform image's digest), because the cache keeps configs by the platform image's manifest digest, and an index has no config. An image's own digest needs no tag file. Without it, the index digests users copy from a registry's page would contact the registry on every Start.
- **A digest reference whose config and layers are cached never contacts the registry.** A layer that's missing, evicted for example, is fetched by digest: the image's manifest by its digest (`repository@digest`), never by tag, then only the missing layers' blobs. The manifest must name the cached config's digest and as many layers as the config has diffIDs. An image with only some of its layers gone keeps its config and its tag.
- **So a Start whose image is cached makes no registry request, and writes nothing to the cache but its layers' and its config's mtimes and its layer link directory (IMG-7).**
- **`force_pull` looks the tag up on every Start, and a registry error then fails that Start (IMG-6).** A new digest rewrites the tag file; the same digest writes nothing. A Start rewrites a tag file only while it still holds what that Start read before its lookup, so a slow cold Start can't put back a digest that a later lookup, force_pull's for example, replaced: tags never expire, so the older digest would stick. Only the plugin writes tag files, so a lock in the plugin makes the compare and the write one step. A digest reference never changes, so `force_pull` doesn't affect it. It travels in `imagecache.Request.ForcePull`; #8 adds the profile key and passes it, and until then the built-in value, false, applies.
- **An image's config and tag are written only after every one of its layers is linked.** Pruning deletes configs with no cached layer, so a config written first could be pruned from under a cold Start. A crash or a cancel mid-pull leaves only layers, which eviction can remove.
- **`Image.Env` comes from the cached config.**
- **Starts share one pull per layer, keyed by its diffID, and one lookup per reference, through `singleflight` (IMG-12).** Concurrent jobs that need the same missing layer share one pull and conversion (#1). A lookup is keyed by the normalised reference, and a `force_pull` lookup shares only with other `force_pull` lookups, so it never gets a cached tag. Two references that resolve to one manifest, a tag and its digest for example, have two lookups and share every layer pull. A layer stored since a Start looked it up is not pulled again.
- **A shared pull runs in a context of its own, not any one job's, and counts the Starts waiting on it.** A Start that is cancelled stops waiting at once and returns its own context's error. The pull is cancelled only when its last waiter leaves, and its temp file is deleted. A pull run in the first job's context would fail every job sharing it when that one job is cancelled; finishing an abandoned pull anyway would spend bandwidth and disk nobody asked for. A later Start that needs the layer, even while an abandoned pull still unwinds, starts a pull of its own. The layer's blob is fetched in the pull's context (go-containerregistry binds a request's context when the layer is made), so the pull's registry requests end with it, whichever Start began it.
- **A layer's blob is read only up to the size the image's manifest declares for it; one that runs past it, or ends short of it, fails that Start with an error naming the layer, and leaves nothing in the cache.** go-containerregistry fetches a blob by its digest alone with no size, and checks the digest only at the blob's end, so a registry that sends endless data, empty gzip members for example, with no Content-Length would otherwise keep the Start pulling until its job's deadline.
- **A shared pull fetches from the source of the Start that began it: its registry, repository and blob digest. A Start whose shared pull fails from another source, other than by the Start's own cancellation, retries once from its own source, sharing that retry with any other Start retrying from the same source; a failure from its own source is final.** The key is the diffID, which an image's author chooses: an image can name a popular base layer's diffID for a blob of its own, and without the retry every Start that joined its pull would fail with its content error.
- **A pull ends with a temp file that every Start waiting on it holds.** Each Start renames it into place only once all of its own image's layers have converted, so IMG-10 still holds for each image: the first Start to get there stores it, and the others find it stored. Once every holder has stored it or failed, an unstored temp file is deleted. A panic in a shared call is recovered inside it and fails only its waiters: `singleflight` would re-panic it in a goroutine of its own and end the plugin (IMG-11).

### Eviction and pruning

- **Eviction runs after each `Release`, and once at startup.** Remove is when layers stop being in use; startup is when the link directories a crash left behind stop counting (Failure handling and startup cleanup, below).
- **The cap counts the allocated size (blocks), not the apparent size, of `<cache>/layers/`, `<cache>/images/` and `<cache>/tags/`.** Blocks are what fill the disk. Temp files don't count: they are pulls still running, and each is bounded by the cap (Image cache, above). (Flagged decision: configs and tags count, and configs no job is using are evicted, below. Counting only layers, as first built, let `images/` and `tags/` grow without bound outside the cap: a config is kept while any one of its layers is cached, so every rebuilt version of a tag that shares a warm base layer left its config and tag behind for good, and an image's author could push many 8 MiB configs naming a popular base layer's diffID. Rejected: a separate cap or count for configs, one more number to tune for the same disk.)
- **Candidates are layers with exactly one link (none in a layer link directory) and image configs not in use, in one list, oldest mtime first,** ties broken by path, so by diffID among layers. A layer's mtime is its last use, set as it is linked; a config's is set as each Start records its image, just after the link. A warm Start refreshes its config's mtime too, so it is a last-use time, like a layer's; IMG-7 allows a cached Start that write (Image cache, above). The hard-link count is a layer's in-use mark, with no counter to keep in step. **A config is in use from its Start's `Acquire`, as its lookup reads it, to that job's `Release`: the same lifetime as its VM's layer links.** A running VM needs only its layers, but with its config gone, and pruning then deleting its tag, the next Start of that image, all of whose layers are cached and in use, would go to the registry, fail while it is down, and might get a different digest from the jobs still running it. The job's hold on its configs is in memory, taken once its Acquire has succeeded and dropped by its Release; a failed Acquire takes none, and nothing of it survives a crash. Eviction deletes candidates until the cache fits its cap; a layer or config in use, or a pinned layer, is never deleted, even over the cap. Under the cap, nothing is deleted. A tag is never a candidate itself: pruning deletes it after its config, so an eviction that stops at the cap may leave the cache under it by those tags' few KiB.
- **A layer an `Acquire` in flight needs is pinned, from the moment its lookup reads the image's config until the Acquire returns, and eviction skips a pinned layer too.** Between an Acquire's look at a cached layer, or the store of one it pulled, and its link, the layer has one link and would otherwise be a candidate; the Acquire's link would then fail. A lookup that finds the config cached reads the tag file and the config, and pins the config's layers, under the same mutex as eviction, so no eviction runs between trusting the cache and the pin: the layers it holds stay, and the Start still makes no registry request (IMG-7). A lookup that goes to the registry pins as soon as it has the config. A shared lookup's result holds a pin of its own until every Start sharing it has taken its own, so a pin per Start covers the handover. The pin is an in-memory count per layer, under the same mutex, and lives only while the Acquire runs; once the Acquire returns, its links mark the layers in use.
- **Pruning keeps the config of an image with a layer pinned, or the config itself in use, and so its tag,** even with none of its layers cached: a Start in flight has looked it up, or a job not yet released runs it. A lookup pins the config, by manifest digest, with its layers, and a successful Acquire hands the config to its job until `Release`.
- **The cap is a byte count passed to `imagecache.New` as an option (`WithMaxSize`), which New requires, 0 or more, so no caller gets an uncapped cache by forgetting it; the plugin passes `cache_max_gib` in bytes (Configuration, above).** A cap of 0 is taken literally: every Release evicts all that no VM is using. There is no MiB key: tests set a tiny cap through the constructor, so no key exists only for tests.
- **Pruning runs after each eviction that deleted something: first every image config with no cached layer left, then every tag whose config is gone.** An image with only some of its layers evicted keeps its config and tag, and its next Start fetches the missing layers by digest (above). Pruning also deletes a damaged config or tag file (Failure handling and startup cleanup, below), and keeps and logs one it can't read.
- **Pruning reads and parses the configs and tags without the mutex below, and takes it only to delete:** under it, it checks that a file is still the one it read (same file, mtime and size: every write renames a new file into place), that the config isn't in use and none of its layers is cached or pinned, and that a tag's config is gone. Configs may be up to 8 MiB each, and a Start's link and record wait on that mutex, so parsing every config under it would stall every Start behind a prune. A file rewritten since it was read is left for the next pruning. Eviction itself, under the mutex, reads only directories and file metadata.
- **Linking, eviction and pruning hold one mutex in the image cache, and so does writing an image's config and tag.** An eviction then can't delete a layer between a job's conversion and its link, or a config while a Start writes it. A Start writes its image's config when the file is missing as it records, not only when its lookup found none, so a config pruned while the Start ran is written again. A tag file pruned while a Start ran isn't: the tag file's compare-and-write (above) sees it changed, and the next Start looks the tag up again.
- **Each eviction is logged, naming the layer or config and its allocated size (LOG-1),** and so is each pruned config and tag. An error while evicting or pruning is logged, not returned by `Release`: it is no job's, and the next `Release` tries again.
- Signature and provenance checks, and removal by age or by reference, are not planned (#5): only cap pressure deletes layers.

## Admission: the memory budget

- **Admission is capped by memory, not by VM count.** The plugin config key `max_memory_mib` caps the sum of `memory_mib` over every running VM, across all jobs. Unset or `0` means no limit: an exception to #1's rule that a plugin-level `0` is taken literally, because a budget of 0 MiB admits no job and would only make every job fail at Create. This replaces #1's `max_vms` (QUE-1): the runner's capacity already caps concurrent jobs, a VM count stops meaning anything once a job brings services, and memory is what actually runs out on a host. No CPU or disk cap is added now; they may come later.
- **A job is admitted with all its VMs at once, or it waits.** Waiting jobs are admitted in arrival order (QUE-2). Admission is never VM by VM, because two half-placed jobs could each hold memory the other needs and deadlock.
- **A job that needs more than `max_memory_mib` on its own fails at Create,** naming its need and the cap. Otherwise it would wait forever. A profile the file defines can't need more on its own: loading the file refuses it (Configuration, above). The implicit `default` can, and services will.
- #10 builds the queue and #8 the config key; this section is the rule they build.

## Failure handling and startup cleanup

- **Each of the state, cache, runtime and listen-socket directories has its own lock: an exclusive, non-blocking `flock` on a `lock` file in that directory** (`<state>/lock`, `<cache>/lock`, `<runtime>/lock`, `<listen>/lock`), held for the plugin's whole life (IMG-16). A single state lock would let two plugins with different state directories share a cache or runtime directory, and then one plugin's startup cleanup would delete the other's live files.
- **The state, cache and runtime directories must be distinct, and none may be inside another.** They are compared as absolute paths with symlinks resolved, before any lock is taken; otherwise startup fails with an error naming both config keys. Startup cleanup deletes `<runtime>/*` without looking: with runtime equal to cache it would wipe the image cache, and with runtime equal to state the kept logs and `bin/`. With state equal to cache, `<state>/jobs/<id>/<n>/` and `<cache>/jobs/<id>/<n>/` collide, so the read-only layer share would expose the VM's scratch disk and logs.
- **The listen-socket directory may be the runtime directory, or its direct parent; otherwise the same rule applies to it** (distinct from the other three, not inside one and not containing one), because cleanup of a directory that contains it would delete the listen socket. The direct parent is allowed because the built-in values have it so (`/run/runner-microvm/` holds the socket and `jobs/`), and nothing cleans the listen-socket directory, so its holding the runtime directory endangers neither. Only the direct parent: a directory further up is a system directory such as `/run`, whose `lock` file the plugin would create and hold. When it is the runtime directory, it takes no lock of its own, since two `flock`s on one file through two opens in one process block each other; the plugin decides that by the directories' file identity, so a symlink can't make it lock the runtime directory's `lock` file twice, and startup cleanup skips the listen socket. The socket itself may not be one of the three directories, nor the lock file of any directory the plugin locks, since binding it would fail on the lock file. No directory may be the lock file of another either, also the runtime directory when the listen-socket directory is its direct parent, since the plugin would create it and then fail to open it as that directory's lock file. Symlinks are resolved through their targets, also targets that don't exist yet, so a dangling link can't hide two directories being one. `check` reports these errors together with the file's decoding errors, comparing only the keys that decoded.
- **The plugin takes the locks in a fixed order: state, cache, runtime, listen-socket directory.** The first one held by another process stops startup with an error naming that directory.
- **The lock files are opened close-on-exec,** so no job process inherits one and keeps a directory locked after the plugin dies.
- **The listen socket is bound last in startup, after the directory locks, startup cleanup and writing the binaries, and its mode is set to 0660 whatever the umask.** A umask-dependent mode is an accident of the service unit; 0660 lets a runner in the socket's group connect and no one else. There is no group key: the socket's group is the process's, or the directory's when it is setgid, since choosing users and groups is the operator's packaging. It is bound under a temporary name in its directory, given its mode, then renamed into place, so no client can connect while the umask's mode is on it. The harness is unchanged: under rootless podman and under rootful Docker its runner connects as the socket's owner.
- **A socket already at the listen socket's path is deleted before binding; any other kind of file there, a symlink included, stops startup, naming the path and what is there.** The listen-socket directory's lock proves no live plugin owns the socket, so it is a crashed plugin's. A regular file or directory there is not the plugin's to delete. A temporary socket a crash left mid-bind is deleted the same way.
- **At startup, after taking every directory lock, the plugin deletes `<state>/jobs/*`, `<state>/bin/*` (stale job binaries and leftover temp files; it then writes the job binary afresh), `<runtime>/*` except `<runtime>/lock` and, when `<listen>` is `<runtime>`, the listen socket, `<cache>/jobs/*` and `<cache>/tmp/*`, without inspecting them (#3's grilling, #25, #97).** The locks prove no other plugin uses these directories. The liveness pipe and Pdeathsig (#52) mean no old job process outlives the plugin. So everything per-job is leftover. Read-only directories in a leftover, which an image or the guest can make, are made writable to delete it, as a Remove does. A symlink is deleted, never followed.
- **Cleanup never deletes a `lock` file, nor, when `<listen>` is `<runtime>`, the listen socket or the temporary name it is bound under (#29).** Deleting a held lock file would let a second plugin lock a new file at the same path. The socket is bound later by this plugin, and listen deletes what is there only when it is a socket (above), so cleanup leaves both names to it rather than deleting a file there that is not the plugin's.
- **Cleanup never touches `<state>/logs/`.** Kept logs must survive restarts; that is what keeping them is for.
- **The plugin's side of startup cleanup, `<state>/jobs/*` and `<runtime>/*`, runs right after the cache's, before the job binary is written, the libraries are checked and the socket is bound,** so no job can be created while it runs.
- **An entry it can't delete stops startup with an error naming its directory, as the cache's cleanup does.** A plugin that serves on top of a leftover it couldn't remove could hand a new job a stale file of the same id.
- **Its deletions are logged as one line with their counts per directory** (`deleted crash leftovers`, with `jobs` for `<state>/jobs/` and `runtime_entries` for `<runtime>/`), and nothing when there were none; an entry it can't delete stops it only after it logs what it deleted before it. The operator learns that the earlier process crashed and what it left.
- **A VM child of the previous plugin still dying at that moment can at worst fail one job.** It was reparented to init, not to the new plugin, so the new plugin can't reap it. The disk `flock` is non-blocking (STO-7), so while the dying VM child still holds it, the first job on that disk fails Start with `disk <source> is in use by another process`. A read-write disk is never shared, so nothing is corrupted.
- **The cache side of startup cleanup is built: `imagecache.New` deletes `<cache>/jobs/*` and `<cache>/tmp/*`, then runs eviction and pruning once (IMG-13).** It runs after every directory lock is taken. The cap may have been lowered across a restart (`cache_max_gib`), and the link directories just deleted may have been the only thing keeping layers in use. Pruning runs even when eviction deletes nothing, because a crash between an eviction and its pruning leaves configs with no layer cached. An entry it can't delete fails startup, naming the cache directory; an eviction or pruning error is logged, as after a `Release`. The deletions are logged as one line with their counts.
- **A cached config or tag file whose content fails the lookup's check is damaged, and is deleted and logged wherever it is found: by a Start's lookup, which then goes to the registry as if the file were missing and writes it again, and by pruning.** Lookup and pruning share one check: a config must parse as an image config; a tag file must be JSON naming the reference whose hash names the file, and a sha256 digest. Every write is atomic and the plugin is the files' only writer, so no crash left a damaged file, and keeping it would fail every Start of that image until a restart or an eviction pruned it. The lookup deletes it under the mutex that linking, eviction and pruning hold. A file that can't be read (a permission or I/O error) fails that Start, naming the file, and is kept, since the next attempt may read it. This replaces #42's rule that a damaged file fails each Start naming it.
- **A layer file is complete when present, and nothing at startup reads layers back to check them.** Every layer is written through a temp file, fsync, rename and fsync of `<cache>/layers/` (Image cache, above), so a crash can't leave a partial one under its real name; a crash mid-pull leaves only temp files, which startup deletes, and complete layers, which the next Start uses, converting only the ones missing.
- **A layer missing when a Start links it is fetched and converted again, once (IMG-15).** Eviction never deletes a layer a Start has pinned (Eviction and pruning, above), so a layer missing there was deleted from under the plugin. The Start pulls whatever its image lacks again, by digest, and links again; a layer missing at that second link fails the Start, with an error naming the layer and the cache directory. One retry is enough for a single deletion, and a loop could spin against something that keeps deleting. The retry's pulls are shared only with other retries, since a pull another Start still holds may be the one whose layer was deleted, and joining it would store nothing. A layer deleted between two Starts needs no retry: the next Start's look at the cache finds it missing and converts it.
- **A job's failure costs that job, never the plugin.** Everything that can hang (the job process, its VMs, the agent) is in a child process or behind a call with a context, and ending the job process ends all of it.

## Logging

- **`log/slog` with the text handler (logfmt) on stderr, the same in all three programs.** It is in the standard library and structured.
- **Where stderr goes:** the plugin's is the operator's; the job process's is its job process log file; each VM child's is its VM's log file; the agent's is its VM's console.
- **Secret values have a type that implements `slog.LogValuer` and redacts itself** (`internal/secret`). This covers LOG-2 wherever a value is logged by accident.
- **The plugin-level key `log_level` sets the level: `debug`, `info`, `warn` or `error`, built-in `info`, read at startup only** (Configuration, above; #98). A change at reload is logged as needing a restart, as for every plugin-level key.
- **The plugin passes it to every job process and VM child in their specs, and to every agent in its boot config, so all three programs follow one setting** (field 8 of the job spec, 16 of the VM child spec and 14 of the boot config). One knob for the operator: the job process log, the VM log and the console all match the plugin's stderr. Each program starts at `info` and sets the level from its spec or boot config before it logs anything else; the plugin, from the config file, before it logs the file it read. A job process, VM child or agent given any other value, the empty one included, fails: only the plugin's bug can send one. libkrun's own lines in the VM log follow `libkrun_log_level` instead (libkrun, above).
- **Events are `info`. What is ignored or degraded is `warn`:** ignored options, a failed flush, an eviction or pruning error, a failed reload, which keeps the running config. **A failure that costs a job or startup is `error`.**
- **Each program logs one `debug` line once it has its level:** the job process the job spec it read, the VM child the libraries it loaded, and the agent the boot config it read, so `debug` shows in every log.

### Responsibilities and import rules

Third-party libraries are free to use except where the boundary test below forbids them. Between our own packages, imports follow this table:

| Package | Responsibility | Our packages it may import | Imported by |
|---|---|---|---|
| `internal/plugin` | `BackendPlugin` server, job table, the two seam interfaces | `imagecache`, `joblaunch`, `agentclient`, `payload`, `config`, `queue`, `logging`, `secret`, the agent and job protocols | `cmd/runner-microvm` |
| `internal/config` | reads and validates the config file | none | `plugin` |
| `internal/imagecache` | pulls, conversion, the cache, layer link directories, eviction | `logging` | `plugin` |
| `internal/joblaunch` | starts a job process, reads its events, kills it | `logging`, the job protocol | `plugin` |
| `internal/agentclient` | the plugin's side of the agent protocol | `secret`, the agent protocol | `plugin` |
| `internal/payload` | the embedded job binary and agent | none | `plugin` |
| `internal/job` | the job process; dispatches `vm` to the VM child | `job/internal/...`, `logging`, `secret`, the job protocol | `cmd/runner-microvm-job` |
| `internal/job/internal/jobnet` | the job network (gvisor-tap-vsock) | `logging` | `job` only (compiler-enforced) |
| `internal/job/internal/vm` | the VM child: libkrun via purego | `logging`, the VM child spec | `job` only (compiler-enforced) |
| `internal/agent` | the agent: boot mounts, the guest's network, Exec, CopyIn, CopyOut, Flush | `logging`, `secret`, the agent protocol | `cmd/runner-microvm-agent`; `plugin`'s tests, only to read the boot root's boot config as the agent does |
| `internal/logging` | slog setup | none | all three programs |
| `internal/secret` | the self-redacting secret type | none | all three programs |

- **The job network and the VM child are nested under `internal/job/internal/`,** so the compiler stops any package outside `internal/job` from importing them.
- **The VM child spec has its own proto package, generated under `internal/job/internal/gen/`.** Only the job binary uses it, so the plugin cannot depend on it.
- **The agent client is its own package (`internal/agentclient`).** Otherwise it drifts into `internal/agent` and pulls host code toward the guest.
- **Code shared by the three programs is only `logging`, `secret` and the generated protocol packages.** Each program's own code stays in its own tree, so a dependency added for one program can't leak into another.
- **Only the plugin's two seams have interfaces:** the image cache and the job launcher, both declared in `internal/plugin`, each with a real and a fake adapter. The data that crosses them is plain: `imagecache.Request` (the job, the VM's index, the image ref and whether to pull again), `imagecache.Image` (digest, image environment, one VM's layer link directory and its layers' names in it) and `joblaunch.Process` (the job process's events and exit). The job launcher reads the job process's stdout to its end whether or not the plugin reads `Events`, and `Events` is buffered for every event the control channel allows for the job spec (one network up and one failed, and one VM started and one VM exited for each VM), so a plugin that stops reading never blocks `Exited` or `Kill`. The seams' contracts on cancel and error:
  - `Launch` that returns an error has killed and reaped every process it started, so no job process is left without a handle to `Kill`.
  - `Exited` closes, and `Kill` returns, only once every process in the job's group has exited and been reaped (Ending a job, above).
  - `Acquire` takes an `imagecache.Request`, not positional arguments, so fields such as per-image registry credentials can be added later without changing callers. It returns one `Image` per VM, whose layer link directory is `<cache>/jobs/<id>/<n>/`, keyed by the VM's index, never its name. Each VM brings its own image once services arrive, so the link directory is the VM's, not the job's. Today only VM 0, the job's container, acquires one, because the plugin protocol passes no VM options for services.
  - `Release` takes only the job, and deletes the layer link directories of all its VMs at once, because a job's VMs are freed together at Remove. It waits for any in-flight `Acquire` for the same job, for any of its VMs, to return before it deletes them, so a cancelled `Acquire` can't finish a link directory after it is deleted and pin its layers against eviction (IMG-14). Then it evicts, and its eviction's errors are logged, not returned.

  Everything else is concrete: an interface with one implementation is a layer with no payoff.

### Boundary enforcement

- **The compiler enforces the nesting under `internal/job/internal/`.**
- **A Go test (`cmd/deps_test.go`) runs `go list -deps` on each binary and asserts:**
  - the plugin binary's dependencies exclude purego, gvisor, gvisor-tap-vsock, `internal/job`, `internal/agent` and forgejo-runner's module;
  - the job binary's dependencies *include* purego and gvisor-tap-vsock, so a renamed import path can't make the check pass silently, and exclude forgejo-runner's module;
  - the agent binary's dependencies are only from an allow-list: the standard library, grpc, protobuf, `vishvananda/netlink` and `moby/sys/user` and the modules they bring in, `internal/agent`, `internal/logging`, `internal/secret` and the agent protocol's generated package.
- **It checks each binary's graph as it ships** (`CGO_ENABLED=0`, and `-tags payload` for the plugin), not as the test process is built, because a file behind a build constraint is in only one of the two.
- **It runs under plain `go test ./...`.** It checks transitive dependencies, which is the property that matters. depguard checks only direct imports, so it isn't used.
- **It lives beside the mains, in `cmd/`,** because it is a test of the binaries, not of any one package.

## Protocols

Three `.proto` files under `proto/`, each in a directory that mirrors its versioned package, beside forgejo-runner's own plugin protocol (`proto/plugin/v1alpha/`, vendored unchanged). The commands are in `docs/development.md` (Protocols and codegen).

| Package | Between | Carries |
|---|---|---|
| `plugin.v1alpha` (the runner's) | runner ↔ plugin (gRPC) | Capabilities, Create, Start, Exec, CopyIn, CopyOut, Remove |
| `runnermicrovm.agent.v1` | plugin ↔ agent (gRPC) | Exec, CopyIn, CopyOut, readiness, the read-write flush; the agent's boot config |
| `runnermicrovm.job.v1` | plugin ↔ job process (control channel) | the job spec in, status events out |
| `runnermicrovm.vm.v1` | job process → VM child | the VM child spec |

- **The `.proto` files define every field #1's behaviours need, not only #4's.** Later epics only add fields. The one exception so far is the job network's names (#64): the job spec's `Network.hosts` and the boot config's `Network.search_domain` described a DNS zone that no longer exists, so they were removed and their numbers and names reserved, which keeps the wire format safe; the boot config's hosts list replaced them.
- **The job spec is job-wide fields plus a list of VMs; the VM child spec is one VM.** The job process starts one VM child for each entry, and status events name the VM by its index (One job process runs all of a job's VMs, above). Today the list always holds one VM, the job's container, because the plugin protocol passes no VM options for services.
- **The agent's boot config is part of the agent protocol's package,** because the agent may import only its own generated package. The plugin builds it, the job spec and the VM child spec carry it unopened, and it reaches the agent as a file in the VM's boot root, binary protobuf (The boot root, above).

- **forgejo-runner's module (`code.forgejo.org/forgejo/runner/v13`) is a test-only dependency.** It brings in about 65 indirect modules, the docker client among them, but none reach a shipped binary: `cmd/deps_test.go` fails if any binary depends on it. Only `cmd/internal/runnerclient`, the test program, imports it outside a test, so `go-licenses` and `govulncheck` see just what its plugin client reaches (`act/plugin`, `act/container`, logrus and creack/pty). Its GPL-3.0-or-later license matches the project's.
- **`cmd/plugin_proto_test.go` checks that the vendored plugin protocol is byte for byte the runner module's copy,** under plain `go test`, so a runner update that changes the protocol fails CI.
- **No test runs its own binary** (`os.Args[0]`, `os.Executable()`). A test that needs a program builds it and runs it by path, with a timeout, and kills its process group on cleanup.
